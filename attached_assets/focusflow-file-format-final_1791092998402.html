FocusFlow V1 format

The .focusflow file

A complete practical reference for people and developer/AI agents who need to create, read, validate, edit, import, export, or build tooling around FocusFlow backups. It combines the human explanation with the exact V1 edge cases that are easy to get wrong.

UTF-8 JSONV1Portable persistent dataHuman-editableNot a ZIP
Mental model: .focusflow is portable persistent FocusFlow data plus enough task/schedule information for the destination app to rebuild derived alarms and other runtime behavior. It is not a dump of the live device.
One important distinction: accepted input and canonical output are not identical. A V1 reader may accept some omitted, legacy, or compatibility forms; a builder should generate the canonical wire names and shapes documented here.

1. File structure

The JSON envelope is authoritative. Metadata and inventories help humans but do not decide what is restored.

Minimum valid V1 input

{
  "kind": "FocusFlowBackupV1",
  "version": 1,
  "settings": {},
  "tasks": []
}

Transport and encoding

  • Content: plain JSON text, UTF-8 encoded.
  • Extension: .focusflow.
  • Archive: none. It is not ZIP, SQLite, or a binary database dump.
  • Provider MIME: current Android file handling may expose application/octet-stream; MIME/filename metadata is not the JSON schema.
  • BOM: a leading UTF-8 BOM may be stripped before parsing.
  • JSON: no comments or trailing commas.
  • Duplicate keys: reject duplicate object keys anywhere in the JSON tree.
  • Unknown fields: may be accepted for compatibility, but are not promised to survive re-export.
Top-level fieldTypeCanonical / input ruleMeaning

versionintegerOPTIONAL INPUT missing = 1; present value must be 1Schema version, not the app version.
exportedAtstringoptional; canonical UTC .sssZExport timestamp.
exportedAtHumanstringoptionalHuman-readable timestamp; informational only.
appVersionstringoptionalSource app version when known; not a schema version.
platformobjectoptionalInformational metadata; current exporter uses {"os":"android"}.
settingsobjectREQUIREDPortable settings payload.
tasksarrayREQUIREDPortable task records. The actual task count is tasks.length.
presetSectionsarrayoptionalDescriptive export inventory. Never treat it as activation instructions.
summaryobjectoptionalDescriptive counts only; never authoritative.
Do not use summary as source-of-truth. If summary.taskCount says 12 while tasks contains 11 objects, the actual task payload is still the 11 objects.

presetSections — inventory only

The current TS exporter uses section IDs such as focus-mode, standalone-block, always-on, daily-allowance, keyword-blocker, block-schedules, and defense. They describe what the export contains. They do not turn features on during restore.

2. Tasks

Tasks are persistent records. Read the values literally and do not confuse imported task status with a live session.

FieldJSON typeV1 rule / semantics
idstring1–128 chars, no control chars, unique inside the incoming file. Current TS IDs are commonly ~21-character nanoid-style values, but imports are not limited to 21 chars.
titlestringRequired and non-blank. Max 1,000 chars.
descriptionstring / null / absentNull or absent normalizes to "". Max 20,000 chars.
startTimestringISO-8601 with Z or explicit offset. Canonical output is UTC .sssZ.
endTimestringSame timestamp rules. Must be ≥ startTime.
createdAtstringISO-8601; canonical output is UTC .sssZ.
updatedAtstringISO-8601; canonical output is UTC .sssZ.
durationMinutesinteger0..100000. A generated file should keep it internally consistent with the exact start/end difference.
statusstringscheduled, active, completed, skipped, overdue.
prioritystringlow, medium, high, critical.
tagsstring[]Max 100/task; each max 100 chars. Missing becomes an empty list.
remindersobject[]Reminder objects, not integer offsets. Max 100/task. Persistent but inert for the Android scheduler.
colorstringMax 32 chars. Missing defaults to #6366f1. Hex is recommended; V1 does not require a strict hex grammar.
focusModebooleanMissing defaults to false.
focusAllowedPackagesarray / null / absentHas distinct inheritance, specific-list, and explicit-empty semantics; see below.

Timestamps and UTC

Generated files should emit all four task timestamps as:

YYYY-MM-DDTHH:mm:ss.SSSZ

Example:

2026-10-04T05:14:00.000Z

Input such as 2026-10-04T10:44:00+05:30 is accepted and normalizes to that UTC instant. There is no task-timezone field. Display time is local-device time; wire time is UTC.

Software should compare parsed instants, not arbitrary raw timestamp strings.

Import status normalization

  • scheduled + future end → scheduled
  • scheduled + past end → skipped, with updatedAt = planNow
  • active + future end → scheduled
  • active + past end → skipped
  • completed / skipped / overdue → preserve

The normal local overdue sweep is deliberately different: unfinished local scheduled/active work whose end has passed may become overdue.

focusAllowedPackages — the easy migration bug

  • Omitted → use global settings.allowedInFocus.
  • null → use global settings.allowedInFocus.
  • Non-empty array → use this task-specific allow-list.
  • Explicit [] → all apps are allowed for this task's focus session.
Do not confuse this with the legacy __block_all__ sentinel. That sentinel belongs to allowed-app presets and is not the meaning of a task-level empty array.

Reminder object

{
  "id": "reminder-001",
  "taskId": "task-001",
  "offsetMinutes": -5,
  "type": "pre-start"
}

type is pre-start, at-start, or post-start. notifId is optional. Offsets are integers. In real legacy data, reminders commonly exist as an empty array.

Reminder semantics

The reminder object is persistent task data, but it is not an Android AlarmManager registration and does not itself constitute a notification.

After restore, the destination derives notification scheduling from task times/status. Do not serialize PendingIntents, notification channels, posted notifications, alarm registrations, or an active FSI as part of the file.

4. Nested portable data

The format carries several structured collections. The following shapes are the compact version of the exhaustive reference.

dailyAllowanceEntries[]

{
  "packageName": "com.example.video",
  "mode": "time_budget",
  "budgetMinutes": 30
}

Supported modes: count, time_budget, interval.

Numeric fields: countPerDay (1..100000), budgetMinutes (1..100000), intervalMinutes (1..100000), intervalHours (1..8760). A clean generated entry should include only the field(s) relevant to its mode.

Canonical package key: packageName. A legacy reader may understand package or dailyAllowanceMs in compatibility input, but builders should not generate those forms.

Named presets

allowedAppPresets[]

{
  "id": "study-apps",
  "name": "Study apps",
  "packages": [
    "com.example.reader",
    "com.example.notes"
  ]
}

blockPresets[]

{
  "id": "social-apps",
  "name": "Social apps",
  "packages": [
    "com.example.social"
  ]
}

Both use id, name, packages[]. Max 500 presets, with max 5,000 packages per list. IDs max 128; names max 1,000.

The legacy __block_all__ sentinel is associated only with allowed-app preset package lists. Do not transfer its meaning to task-level focus lists.

recurringBlockSchedules[]

{
  "id": "evening",
  "name": "Evening block",
  "packages": ["com.example.social"],
  "days": [1, 3, 5],
  "startHour": 21,
  "startMin": 0,
  "endHour": 22,
  "endMin": 30,
  "enabled": true,
  "vpnEnabled": false,
  "vpnPackages": []
}
  • id: non-blank, max 128 chars.
  • name: non-blank, max 1,000 chars.
  • packages: valid package IDs, max 5,000.
  • days: distinct integers 1..7.
  • time: hours 0..23, minutes 0..59.
  • enabled: boolean; compatibility input may default it to true when omitted.
  • vpnEnabled: boolean; compatibility input may default false.
  • vpnPackages: optional package list, max 5,000.
Wire day numbering: 1=Sunday, 2=Monday, 3=Tuesday, 4=Wednesday, 5=Thursday, 6=Friday, 7=Saturday. This is different from the Kotlin internal 0-based convention. Overnight windows such as 22:00 → 07:00 are valid and must be preserved.

An enabled recurring schedule must have at least one valid package under the V1 normalizer. Disabled schedules may be empty in compatibility input.

greyoutSchedule[] — user windows and derived windows are different

User-authored window: no scheduleId

{
  "pkgs": ["com.example.social"],
  "startHour": 22,
  "startMin": 0,
  "endHour": 23,
  "endMin": 30,
  "days": [1, 2, 3, 4, 5]
}

A legacy single-package form may use pkg instead of pkgs.

Derived window: has scheduleId

{
  "pkgs": ["com.example.social"],
  "startHour": 22,
  "startMin": 0,
  "endHour": 23,
  "endMin": 30,
  "days": [1, 2, 3, 4, 5],
  "scheduleId": "evening",
  "scheduleName": "Evening block",
  "vpnEnabled": false
}

Derived rows are generated from authoritative recurring schedules and should not be mistaken for independent user-authored rules.

Import rule: keep entries without scheduleId; discard entries with scheduleId; restore recurringBlockSchedules; regenerate the derived windows from those schedules. This avoids stale/duplicated derived state.

Window validation: hours 0..23, minutes 0..59, days distinct 1..7, and a valid pkg or non-empty valid pkgs is required. Max 5,000 windows.

If a recognized userProfile field fails validation, the whole profile object may be ignored with a warning while the rest of the backup proceeds. Import does not reproduce legacy UI write-through behavior: focusSessionLength does not silently rewrite defaultDuration or pomodoroDuration.

Package references

Canonical Android package identifiers match:

^[A-Za-z][A-Za-z0-9_]*(\.[A-Za-z0-9_]+)+$

Maximum length is 255 characters; package-list maximum is 5,000 entries. A referenced package does not need to be installed on the destination. Preserve a valid reference even when it is unresolved. Never substitute an app label, a similarly named package, or an installed “equivalent”.

Task color and focus mode

color is just a string (max 32 chars), with #6366f1 as the missing-value default. Hex is recommended, but V1 does not require a strict hex grammar. focusMode is boolean and defaults to false when absent.

A backup can carry persistent truth without carrying live Android state, security secrets, or foreign-device resources.

Never apply these 21 live-state keys

Even if an old V1 file contains them, the current reader must never turn them into active destination-device state.

Keep local / accept-and-ignore

These can occur in older or compatibility-oriented files but are not active portable V1 settings:

  • weekStartDay — legacy value; do not overwrite the destination's actual preference.
  • defaultReminderOffsets — legacy/unused scheduler configuration; not an active V1 reminder scheduler contract.
  • launcherPinnedPackages, beginnerMode, tipsCardDismissed, tipsCardFirstShownAt, lastShownStreakMilestone, pendingAchievementCelebration, pendingPresets — accepted/ignored legacy data.
  • launcherWallpaperUri, overlayWallpaper — device-local/external resource references; never import a dangling foreign-device URI.
  • onboardingComplete, privacyAccepted — destination-local consent/onboarding state.

Security and runtime examples

Do not restore active focus sessions, live blocking switches, current enforcement state, PIN/security state, notification master state, or raw AlarmManager registrations. These belong to the destination environment.

System-protected packages

A backup is not an override channel for device/system protections. The documentation deliberately does not treat a hard-coded protected-package list as part of the .focusflow wire contract.

6. Import rules

FocusFlow validates and normalizes the file before persistent mutation. File-level failures are separated from task-local warnings.

Whole-file rejection

  • Invalid/malformed JSON or UTF-8.
  • Root is not an object.
  • kind missing or wrong.
  • settings missing or not an object.
  • tasks missing or not an array.
  • Present version is not 1.
  • Duplicate JSON object key at any depth.
  • Any hard parser/resource limit is exceeded.
  • Duplicate task ID inside the incoming tasks[].
  • Unsupported protectionMode enum.

Task-local / field-local problems

Some invalid records can be dropped or normalized while the remaining import continues. Examples include malformed task fields, invalid package list items, and invalid individual reminder items.

  • Invalid reminder item → drop reminder + warning; keep task.
  • Invalid package item → drop item + warning where the field permits this normalization.
  • Invalid setting value → ignore that setting + warning.
  • Invalid userProfile object → ignore the profile + warning.

Conceptual restore flow

1

Obtain the .focusflow content from local storage, a provider, Drive, Files, USB, email attachment, or another file source.

2

Decode bounded UTF-8 and perform duplicate-key / structural validation.

3

Normalize timestamps, task status, package entries, and other field-specific compatibility forms.

4

Build an import preview: tasks, settings sections, ignored legacy fields, warnings, external resources, and conflicts where local state is available.

5

User confirms settings and task mode (Merge or Replace).

6

A restore plan is staged; persistent mutation occurs only after preflight succeeds.

7

Persistent data is restored. Derived alarms/notifications are then rebuilt from destination task/settings truth.

8

Result and warnings are surfaced. Unresolved package/resource references remain identifiable rather than being silently replaced.

Import preview

Before persistent mutation, the preview/plan can distinguish tasksInFile, newTasks, identicalDuplicates, conflictingTasks, invalidByReason, pastScheduledToSkipped, settingsSectionsPresent, externalResourcesUnresolved, and warnings. Destination-specific conflicts cannot be known by a web-only builder unless local destination data is supplied.

Merge

  • New task ID → insert the incoming task.
  • Same ID + identical semantic content → duplicate; skip incoming record and keep existing task.
  • Same ID + divergent semantic content → reject the entire restore before mutation with an ID conflict.

This is deliberate product semantics, not a silent “insert-or-ignore” database shortcut.

Replace tasks

  • Deletes existing task rows and inserts the valid incoming task set in one task-level transaction.
  • Does not mean “factory reset” or “replace the entire app.”
  • Leaves analytics/history, focus-session history, PIN/security state, consent, and other device-local runtime state untouched.
  • Blocked while a Focus Session is active.

Merge duplicate projection

Same-ID tasks are compared using:

title
+ description
+ startTime
+ endTime
+ durationMinutes
+ status
+ priority
+ tags
+ color
+ focusMode
+ focusAllowedPackages

createdAt and updatedAt are excluded. reminders[] is intentionally excluded from V1 conflict identity even though it is preserved as task data. Strings are exact/case-sensitive; no implicit trimming or Unicode normalization. Set-like collections are compared in deterministic canonical order, and timestamps are compared as normalized instants.

Repeated imports

There is no permanent “this backup was already imported” block. Re-importing the same file is allowed. Existing equivalent task IDs become duplicates on subsequent Merge imports, while portable settings are re-applied according to their field policies.

External opening on Android

Opening a .focusflow file from a file manager/provider is simply another import entry point:

ACTION_VIEW
→ receive URI
→ read content
→ validate / normalize
→ stage pending import
→ show import confirmation
→ restore

The provider's filename/MIME metadata is transport metadata; the parsed JSON envelope is the actual content contract.

8. Persistent vs runtime/derived state

The file contains portable truth. Android rebuilds operational objects after restore.

Portable persistent truth

Tasks, portable settings, presets, recurring schedules, user profile data, and user-authored greyout windows.

Stored in the file and eligible for restore.

Persistent but inert

Task reminder objects. They survive as task data but do not equal concrete notification registrations.

Stored, but scheduler behavior is derived separately.

Runtime / device-local / derived

Active session state, live blocking, enforcement switches, notification registrations, AlarmManager registrations, PendingIntents, PIN/security state, consent, local URIs, and other device setup.

Do not serialize these as authoritative portable state.

What happens to alarms after import?

For future imported tasks that qualify for scheduling, FocusFlow derives task-end alarms from task persistent data. The V1 product policy is an exact task-end timing commitment: if exact-alarm capability is unavailable, the task stays persisted but task-end scheduling is marked deferred (for example, DEFERRED_EXACT_UNAVAILABLE) rather than silently downgraded to an inexact task-end alarm. Advisory reminder notifications may use an inexact/degraded tier because they are approximate by nature.

Generic reminder scheduling is also derived from task time data through a separate planner/chain. Concrete AlarmManager IDs, notification registrations, and runtime journals are not .focusflow fields.

9. Canonical export and rebuild behavior

A builder should generate canonical V1 data, not merely data that happens to pass a permissive reader.

Canonical export construction

1

Gather portable settings. Include the 26 current APPLY keys using the exact V1 wire names. Include focusMirrorVpnEnabled even when false.

2

Build greyoutSchedule. Combine user-authored windows with derived windows generated from the enabled recurring schedules.

3

Keep recurringBlockSchedules separately. It remains the authoritative recurring source.

4

Strip non-portable state. Do not export the 21 never-apply keys, consent/onboarding state, or canonical wallpaper URIs.

5

Canonicalize task timestamps. Emit UTC .sssZ values.

6

Preserve task data. Keep persistent task fields and reminder objects; never invent Android scheduler registrations.

7

Build descriptive metadata. exportedAt, exportedAtHuman, platform, presetSections, summary, and appVersion when known.

8

Serialize valid JSON. No comments, trailing commas, or duplicate object keys.

9

Save with .focusflow. Recommended filename: focusflow-YYYY-MM-DDTHH-mm-ss.focusflow.

Advanced runtime note: derived reminder slots are not stored in the file

The runtime planner may derive slots such as <taskId>-pre-600000 (10 minutes before start), <taskId>-pre-300000 (5 minutes), <taskId>-pre-60000 (1 minute), <taskId>-pre0 (at start), <taskId>-mid900000 (15 minutes after start), <taskId>-mid1800000 (30 minutes after start), an almost-end slot, and <taskId>-end for the task-end event. These identifiers are implementation/runtime data only. The generic reminder chain has a global slot budget of 450 and avoids scheduling slots that are effectively already due; task-end handling is separate.

Import does not simulate source-device runtime

An imported active task never resurrects the source device's live focus session. Past scheduled/active tasks are normalized to skipped at import planning time so the destination does not create stale immediate task-end behavior.

Derived reminder context

The runtime reminder planner may derive slots such as pre-start notices, at-start, mid-session check-ins, an “almost end” notice, and the task-end event. These concrete slots and identifiers are runtime implementation details, not wire schema fields.

11. Rules for a builder or integration

A web builder, migration tool, or AI agent should distinguish canonical generation from permissive reading.

When generating

  • Emit kind = FocusFlowBackupV1 and version = 1.
  • Use exact V1 wire names.
  • Emit canonical UTC timestamps.
  • Generate unique task IDs.
  • Keep durationMinutes coherent with start/end.
  • Validate Android package syntax but do not require the package to be installed.
  • Use reminder objects, not integer offsets.
  • Keep recurring schedules separate from greyout windows.
  • Use summary as descriptive output only.
  • Never emit the 21 live-state keys or foreign-device wallpaper URIs.
  • Save as UTF-8 JSON with .focusflow extension.

When reading

  • Validate the envelope before mutation.
  • Reject duplicate JSON keys and duplicate incoming task IDs.
  • Accept missing version as V1; reject another present version.
  • Normalize accepted timestamp offsets to UTC instants.
  • Apply only the portable settings table.
  • Keep omitted settings local; overwrite present valid settings.
  • Normalize imported scheduled/active tasks using the import-time status rules.
  • Never resurrect a source live session or device enforcement state.
  • Report warnings for dropped/ignored fields instead of silently hiding them.
  • Rebuild alarms/notifications from persistent truth after restore.

Builder acceptance checklist

  • UTF-8 decode succeeds and the JSON parses.
  • No duplicate object keys.
  • Top-level object contains valid kind, settings, and tasks; version is 1 or omitted.
  • All task IDs are unique inside the file.
  • All timestamps are valid; endTime ≥ startTime.
  • Duration is coherent for generated examples.
  • Task statuses/priorities are valid.
  • Reminder entries are objects with valid types.
  • Package lists use syntactically valid Android package IDs.
  • Recognized settings have valid types, ranges, and enums.
  • Resource limits are respected.
  • Summary counts are derived from actual payload arrays.
  • No runtime-only state is presented as portable truth.
  • presetSections remains descriptive.

12. Plain-English summary

This is the compact version for a normal user who does not need the technical reference.

What a backup contains

Tasks, portable preferences, blocking words and schedules, presets, launcher preferences that are explicitly portable, profile data, and enough persistent information for FocusFlow to rebuild derived behavior on another device.

What a backup does not contain

It does not carry a live focus session, current enforcement state, PIN/security secrets, consent/onboarding decisions, registered alarms, posted notifications, or foreign-device local file URIs.

One sentence: .focusflow = portable persistent FocusFlow data + task/reminder data + enough information to reconstruct useful derived scheduling; not a live Android state dump.
