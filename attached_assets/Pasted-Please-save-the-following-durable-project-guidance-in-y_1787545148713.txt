Please save the following durable project guidance in your project memory.
FocusFlow testing must remain feature-led and architecture-led. All FocusFlow test implementation and test configuration must stay inside the separate artifact boundary:
artifacts/focusflow/
Keep React/TypeScript tests, Kotlin/native tests, React↔Kotlin contract tests, fixtures, and test configuration associated with this artifact. Do not place FocusFlow tests in the mockup sandbox, FocusFlow-pc, or a shared unrelated test directory.
Treat these as separate evidence layers:
1. React/TypeScript unit tests
2. React service/orchestration tests with mocks
3. Kotlin policy/JVM tests
4. Android/Robolectric tests
5. React↔Kotlin boundary contract tests
6. Real Android emulator/device tests
A passing React mock test does not prove that Kotlin enforcement or Android lifecycle behavior works. Cross-layer tests must verify the actual shared contracts: SharedPreferences keys, JSON payloads, task/session IDs, timestamps, package names, enabled states, remaining durations, native events, malformed data, missing data, and unavailable-native states.
Generated Android output must never be the only durable home of native tests. Before choosing the Kotlin test location, inspect how Expo prebuild and android-native/install.sh work. If expo prebuild --clean regenerates or deletes the Android project, keep the durable native test source under the FocusFlow/native source boundary and install or copy it through the established native integration path.
Run testing in this order:
1. Replit-local typecheck and JavaScript tests
2. Any Kotlin JVM/Robolectric tests that are genuinely runnable locally
3. Grouped GitHub Actions validation
4. Emulator/device tests through GitHub Actions or another Android-capable environment
5. Relevant GitHub CodeQL review
Do not create one workflow or Actions job per feature or test file. Use one grouped FocusFlow test workflow with a small number of jobs: JavaScript/contracts, Android JVM/Robolectric, and optional device tests. Keep Replit workflows for app serving/previewing, not as a substitute for Android Studio or an emulator.
Tests must be deterministic. Use fixed clocks, explicit timezones, isolated databases/files, seeded randomness, reusable fixtures, failure injection, idempotency checks, and repeated concurrency tests. Never turn a failed native operation into a passing “enabled” or “enforced” assertion. Distinguish real failures from unavailable Android infrastructure.
After local tests and CI evidence are satisfactory, review only CodeQL alerts, issues, and closed cases relevant to artifacts/focusflow. Ignore FocusFlow-pc, mockup/demo artifacts, unrelated packages, and historical findings that do not apply to the current mobile app. Compare each relevant closed finding with the current code and add regression coverage only when the security behavior has a real testable contract.
Use approved workspace integration or secret mechanisms for GitHub access. Never place tokens or credentials in memory, source files, fixtures, logs, reports, or chat.
Do not store a test-by-test changelog, test counts, temporary CI results, device data, credentials, or file lists that can be discovered from the repository. Store only durable constraints like the artifact boundary, test-layer separation, generated-Android limitation, local→CI→CodeQL order, and FocusFlow-only CodeQL scope.
