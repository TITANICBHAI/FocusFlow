Canonical developer reference · V1

.focusflow File Format

This page is the rendered canonical specification for FocusFlow’s native backup/exchange document. It includes the wire contract, task/reminder structures, portable settings, runtime boundaries, validation rules, import/export semantics, Android external-file behavior, and builder requirements.

UTF-8 JSONExtension: .focusflowWire kind: FocusFlowBackupV1Version: 1No ZIP container
Canonical generation rule: generate the stable TS V1 public field names, while satisfying the compatible Kotlin V1 parsing rules documented below. Kotlin internal property names are never public file-field names.
Important: a valid .focusflow file is portable persistent configuration + task data. It is not a dump of active FocusFlow runtime state, current blocking state, PIN state, or live Android scheduler registrations.

Purpose: This document is the authoritative content specification for rebuilding the .focusflow documentation/reference page and the .focusflow backup builder. An HTML agent given this document should be able to explain the format precisely and generate a valid FocusFlow V1 file without needing the TS source.

Source basis reviewed:

  • Existing TS hybrid: focusflow.zip — src/services/backupService.ts, src/data/types.ts, src/data/defaultSettings.ts, src/services/protectedApps.ts, task/focus services.
  • Current Kotlin migration: files.zip — BackupEnvelopeV1.kt, BackupV1Exporter.kt, TsSettingsAdapter.kt, BackupJsonLimits.kt, BackupSettingsPolicy.kt, Task.kt, AppSettings.kt, notification/reminder scheduler code.
  • Existing HTML pages: focusflow-backup-builder.html and .focusflow File Format Reference HTML.

1. Critical rule: one source of truth

The current HTML pages contain several contradictions. The rebuilt documentation must not repeat them. The page content should distinguish:

Observed TS V1 wire behavior
Current Kotlin V1 reader/writer behavior
Target/canonical `.focusflow` generation rules
Runtime/device-local behavior

For a file-generation page, the canonical generated V1 profile is the stable TS wire naming plus the Kotlin V1 parsing rules that are compatible with that wire format. Kotlin internal property names must never become public file-field names.

2. What the current HTML gets wrong / must be corrected

Top-level keys

The reference page says every file must contain exactly the listed keys. That is too strong: appVersion is optional in the TS envelope, version may be omitted by the current V1 reader and interpreted as 1, and metadata fields are not all authoritative. For generated files, emit version: 1, appVersion when known, presetSections, and summary.

“Entire state”

Do not say .focusflow exports the entire runtime/device state. It exports portable persistent configuration + task data. Active focus, live blocking, notification/master runtime switches, PIN state, and other device-local state are deliberately not restored.

Task requiredness

The existing reference page marks description, tags, reminders, color, and focusMode as required. The Kotlin V1 parser accepts these as missing and applies defaults (description -> , tags -> [], reminders -> [], color -> #6366f1, focusMode -> false). The canonical generator SHOULD emit them explicitly anyway.

Reminders

The reference page incorrectly describes reminders as integer offsets. The actual TS/Kotlin V1 wire shape is an array of reminder objects with id, taskId, offsetMinutes, type, and optional notifId.

focusAllowedPackages: []

Do not describe empty array as “all apps allowed”. The TS UI comment says that, but the actual focus enforcement path converts an empty effective allow-list to com.focusflow.internal.blockall, so the effective native behavior is block-all except protected packages. Generated files should omit the key to inherit the global setting unless an explicit empty custom allow-list is intentionally desired.

Time format

The current reference page says all input times must be UTC with Z. The Kotlin V1 reader accepts ISO-8601 offsets as well and normalizes them to canonical UTC. The generator should emit canonical Z timestamps.

Summary

summary is metadata, not the source of truth. Generated files should calculate it from payload data; import previews should calculate counts from validated payloads, not trust summary values.

Import semantics

The reference page says importing replaces all existing data. That is false. The product has a review step, settings/task section selection, task merge/replace semantics, and field-specific settings policies.

Preset sections

presetSections are descriptive inventory/preview metadata. They are not commands to activate live blocking.

Protected packages

Do not use a short illustrative list only. The page should document the exact protected list used by the TS source and explain that these packages cannot be blocked by FocusFlow's blocking configuration.

Validation limits

The builder and Kotlin parser have concrete resource limits. The reference page currently omits several of them.

3. File identity and transport

Property Canonical V1 value / rule
Extension .focusflow
Internal encoding JSON text, UTF-8
Current MIME application/octet-stream
Wire kind FocusFlowBackupV1
Wire version 1 for canonical generated files
Export filename focusflow-YYYY-MM-DDTHH-mm-ss.focusflow
Archive/container None. A .focusflow file is not a ZIP.

The file may be copied through storage providers, email, Drive, Files, USB, etc. Provider MIME and filename metadata are discovery metadata; once FocusFlow receives the content, the actual envelope is authoritative.

4. Canonical top-level V1 schema

Canonical generated structure:

{
  "kind": "FocusFlowBackupV1",
  "version": 1,
  "exportedAt": "2026-09-01T01:30:00.000Z",
  "exportedAtHuman": "01/09/2026, 07:00:00",
  "appVersion": "1.0.6",
  "platform": {
    "os": "android"
  },
  "settings": {},
  "tasks": [],
  "presetSections": [],
  "summary": {
    "taskCount": 0,
    "blockedWordCount": 0,
    "greyoutWindowCount": 0,
    "dailyAllowanceCount": 0
  }
}
Field Required for canonical generation Semantics
kind Yes Must be exactly FocusFlowBackupV1.
version Yes Integer 1. Current Kotlin V1 reader also accepts omission as V1 for compatibility.
exportedAt Yes Export instant. Emit canonical UTC ISO-8601 with Z.
exportedAtHuman Yes in exporter output Human display string only; not used for restore semantics.
appVersion Optional Diagnostic metadata. Does not control schema compatibility.
platform Optional metadata Informational, e.g. { "os": "android" }; not a basic validity gate.
settings Yes Object containing portable V1 settings fields.
tasks Yes Array of task objects.
presetSections Strongly recommended / exporter emits Descriptive inventory; not live activation commands.
summary Strongly recommended / exporter emits Derived metadata; never authoritative during import.

Summary rules

For generated files:

  • summary.taskCount MUST equal tasks.length.
  • blockedWordCount SHOULD equal the number of exported settings.blockedWords entries.
  • greyoutWindowCount SHOULD equal the number of actual exported settings.greyoutSchedule windows.
  • dailyAllowanceCount SHOULD equal the number of exported settings.dailyAllowanceEntries entries.
  • The importer must still calculate real counts from payload content.

5. Task object — canonical field reference

Canonical generator output should include all core fields explicitly.

Field Type Canonical rule
id string Stable task identifier. Non-empty; max 128 chars; no control chars. Existing FocusFlow IDs are nanoid-style, but the parser does not require a specific alphabet beyond string/control checks. Must be unique within the file.
title string Non-blank; max 1,000 chars.
description string Emit a string; "" is valid. Current reader also converts missing/null to "".
startTime string ISO-8601 instant. Generator should emit YYYY-MM-DDTHH:mm:ss.SSSZ. Reader accepts Z or explicit offset.
endTime string ISO-8601 instant; must not be before startTime; generator should satisfy end-start = durationMinutes.
durationMinutes integer Whole minutes. Kotlin V1 parser accepts 0..100000; normal product-created tasks should normally be positive. Generator should derive it from start/end rather than inventing an inconsistent value.
status enum scheduled / active / completed / skipped / overdue.
priority enum low / medium / high / critical.
tags string[] Emit array; max 100 tags/task, each max 100 chars. [] allowed.
reminders Reminder[] Emit array of reminder objects, not integer offsets. Max 100/task in current Kotlin parser.
color string Hex/task color string; current parser allows up to 32 chars and defaults missing to #6366f1.
focusMode boolean true activates task-time blocking behavior; false does not. Missing defaults to false.
focusAllowedPackages string[] / null / absent Absent or null means no per-task override; effective policy comes from global settings.allowedInFocus. Non-empty array is a task-specific allow-list. Empty array is an explicit empty allow-list and can lead to the native block-all sentinel; do not use casually.
createdAt string ISO-8601 instant.
updatedAt string ISO-8601 instant.

Task invariants

task.id unique within file
endTime >= startTime
durationMinutes = (endTime - startTime) / 60_000
all four timestamps parse as instants
known status/priority enums only

Past scheduled task on import

If an imported task has status = scheduled and its endTime is earlier than the captured import now, the target restore contract normalizes it to skipped and does not create a future alarm for it. This is not a reason to change historical completed/skipped/overdue tasks.

6. Reminder object — canonical shape

{
  "id": "reminder-001",
  "taskId": "task-001",
  "offsetMinutes": -5,
  "type": "pre-start",
  "notifId": "optional-device-id"
}
Field Rule
id Non-empty stable reminder identity; max 128 chars in current parser.
taskId Parent task ID. On restore, rewrite this field if the parent task ID is remapped.
offsetMinutes Integer offset relative to the task schedule. Preserve exactly. The current persistent model supports negative/zero/positive values.
type pre-start, at-start, or post-start.
notifId Optional string/null. Treat as device-derived notification bookkeeping unless the current exporter explicitly preserves a value; do not invent one merely to generate a backup.

Critical distinction

Task.reminders[] is persistent task data. It is not automatically identical to the generated Android notification/alarm registrations. The current Kotlin reminder scheduler independently derives task-relative notification slots. The docs must not claim that every Reminder object directly maps one-to-one to an Android AlarmManager registration.

7. Focus Mode and allowed packages

Global list:

"allowedInFocus": [
  "com.android.phone",
  "com.whatsapp",
  "com.example.music"
]

Per-task override:

{
  "focusMode": true,
  "focusAllowedPackages": [
    "com.whatsapp",
    "com.example.music"
  ]
}

Resolution model:

focusAllowedPackages absent
    → use settings.allowedInFocus

focusAllowedPackages null
    → no task-specific override; use global setting

focusAllowedPackages non-empty
    → use task-specific list

focusAllowedPackages empty array
    → explicit empty effective allow-list
    → native focus service maps empty effective list to
      com.focusflow.internal.blockall
    → blocks every non-protected foreground app

Package names are exact Android package IDs. Never document label/name matching as a portability mechanism.

11.1 AllowedAppPreset

{

  "name": "Study tools",

    "com.example.reader",

  • name: string, max 1,000 chars.
  • packages: Android package IDs; current parser allows an empty array for the allowed-preset case.

11.2 BlockPreset

{
  "id": "social",
  "name": "Social apps",
  "packages": [
    "com.instagram.android",
    "com.reddit.frontpage"
  ]

  • Same identity/name rules.
  • packages are exact package IDs.

11.3 DailyAllowanceEntry

{
  "packageName": "com.example.video",
  "mode": "count",
  "countPerDay": 3,
  "budgetMinutes": 30,
  "intervalMinutes": 5,
  "intervalHours": 1
}
Field Rule
packageName Exact Android package ID.
mode count, time_budget, interval.
countPerDay Integer 1..100000 when used.
budgetMinutes Integer 1..100000 when used.
intervalMinutes Integer 1..100000 when used.
intervalHours Integer 1..8760 when used.

Compatibility note: the Kotlin adapter also understands a legacy/internal package alias and can derive dailyAllowanceMs, but a hand-generated canonical TS-wire file should use packageName and the documented mode-specific fields.

11.4 RecurringBlockSchedule

{
  "id": "evening",
  "name": "Evening block",
  "packages": ["com.example.social"],
  "days": [1, 3, 5],
  "startHour": 21,
  "startMin": 0,
  "endHour": 22,
  "endMin": 30,
  "enabled": true,
  "vpnEnabled": false,
  "vpnPackages": []
}
  • days are 1..7 using the TS/Java Calendar convention: 1=Sunday, 2=Monday, …, 7=Saturday.
  • startHour/endHour: 0..23.
  • startMin/endMin: 0..59.
  • enabled, vpnEnabled: booleans.
  • vpnPackages: optional package list; when empty and VPN is enabled, the schedule may use the schedule’s app package list according to current feature semantics.

11.5 GreyoutWindow

{
  "pkg": "com.example.video",
  "pkgs": ["com.example.video"],
  "startHour": 9,
  "startMin": 0,
  "endHour": 10,
  "endMin": 0,
  "days": [2],
  "vpnEnabled": false
}
  • pkg is the backward-compatible primary package field.
  • pkgs can contain multiple packages and overrides pkg when present.
  • scheduleId / scheduleName identify derived windows produced from recurring schedules; they should not be used for ordinary user-created greyout windows, and the Kotlin V1 normalizer drops derived windows containing scheduleId from direct greyoutSchedule application.
  • days use 1..7.

11.6 UserProfile

Recognized profile fields:

  • name — string
  • occupation — string
  • dailyGoalHours — number
  • wakeUpTime — string
  • focusGoals — string[]
  • sleepTime — string
  • chronotype — 'morning' | 'midday' | 'afternoon' | 'evening' | 'night' | 'flexible'
  • focusSessionLength — number
  • breakStyle — 'short_frequent' | 'balanced' | 'long_infrequent' | 'no_break'
  • distractionTriggers — string[]
  • motivationStyle — string[]
  • weeklyReviewDay — 'sun' | 'mon' | 'tue' | 'wed' | 'thu' | 'fri' | 'sat'

Current Kotlin V1 validation rules for the profile include:

  • wakeUpTime, sleepTime: HH:mm.
  • dailyGoalHours: 1..16.
  • focusSessionLength: 1..480.
  • chronotype: morning | midday | afternoon | evening | night | flexible.
  • breakStyle: short_frequent | balanced | long_infrequent | no_break.
  • weeklyReviewDay: sun | mon | tue | wed | thu | fri | sat.
  • focusGoals, distractionTriggers, motivationStyle: bounded string arrays.

12. presetSections — descriptive inventory, not activation

The current TS exporter builds these section IDs:

  • focus-mode
  • standalone-block
  • always-on
  • daily-allowance
  • keyword-blocker
  • block-schedules
  • defense

The structure is:

{
  "id": "focus-mode",
  "name": "Focus Mode",
  "configured": true,
  "appPackages": ["com.example.music"],
  "itemCount": 2,
  "details": {
    "allowedAppPresets": []
  }
}

Possible fields:

  • id: known section ID.
  • name: display name.
  • configured: boolean.
  • appPackages: optional string array.
  • vpnPackages: optional string array.
  • itemCount: optional integer.
  • details: optional descriptive object.

Semantics:

presetSections describe what the backup contains
presetSections do NOT activate live blocking
presetSections do NOT resurrect timers
presetSections do NOT override the chosen import options

13. Portable vs runtime data model

This distinction should be visible on the documentation page.

Layer Examples In .focusflow?
Persistent portable truth tasks, portable settings, presets, schedules, profile Yes
Derived OS state AlarmManager registrations, notification requests Recreated, not serialized as authoritative runtime state
Runtime/session state active focus session, current blocking state, current task session allow-list No
Device-local setup/security onboarding/consent, PIN state, live enforcement switches No
External resources local wallpaper/file URIs Only when an explicit transferable representation exists; never assume a local URI is portable

This is one of the most important concepts for agents generating or modifying files.

15. Time and timezone rules

15.1 Absolute task timestamps

  • Use ISO-8601 instants.
  • Canonical generated form: UTC Z, e.g. 2026-09-01T01:30:00.000Z.
  • The Kotlin V1 reader accepts an explicit offset too and converts it to the same instant.
  • exportedAtHuman is display metadata and is not a timezone authority.

15.2 IST example

10:00 04:30Z

15.3 Recurring schedules

Recurring schedules are wall-clock rules. The documentation must state the chosen timezone ownership clearly. For the current target, preserve explicit schedule data and let the destination device apply it in its local schedule context unless a future format version introduces an authoritative stored timezone.

17. Validation and resource limits — current Kotlin V1

| MAX_FILE_BYTES | 8 MiB | whole UTF-8 input | | MAX_DEPTH | 12 | JSON nesting depth | | MAX_JSON_NODES | 2,000,000 | total parsed/scanned nodes | | MAX_TASKS | 20,000 | top-level tasks | | MAX_STRING_CHARS | 20,000 | generic string | | MAX_TITLE_CHARS | 1,000 | task/preset title | | MAX_TAG_CHARS | 100 | each tag | | MAX_ID_CHARS | 128 | task/reminder/preset IDs | | MAX_PACKAGE_CHARS | 255 | Android package strings | | MAX_PACKAGES_PER_LIST | 5,000 | package list | | MAX_BLOCKED_WORDS | 5,000 | blocked words | | MAX_BLOCKED_WORD_CHARS | 200 | each blocked word | | MAX_ALLOWANCE_ENTRIES | 1,000 | daily allowance entries | | MAX_RECURRING_SCHEDULES | 500 | recurring block schedules | | MAX_GREYOUT_WINDOWS | 5,000 | greyout windows | | MAX_PRESETS | 500 | preset arrays | | MAX_OVERLAY_QUOTES | 500 | overlay quote entries | | MAX_TAGS_PER_TASK | 100 | tags in one task | | MAX_REMINDERS_PER_TASK | 100 | reminders in one task |

Strict input rules:

  • Invalid UTF-8 is rejected; malformed bytes are not repaired with replacement characters.
  • Duplicate JSON object keys are rejected before the JSON tree is treated as valid.
  • Standard JSON only: no comments, no trailing commas.
  • Unknown optional fields may be tolerated for compatible V1 reading.
  • Unknown enum values must not silently fall back to a default meaning.
  • Structural limits are checked before uncontrolled memory allocation.

18. Import semantics for users and agents

The documentation must show the complete conceptual flow:

obtain `.focusflow`
      ↓
FocusFlow validates envelope
      ↓

Merge

  • Preserve an incoming task ID when it does not already exist.
  • Same incoming ID + semantically equivalent local task → duplicate/skip.
  • Same incoming ID + materially different local task → explicit conflict; never rely on Room INSERT OR IGNORE to decide.
  • Deliberate re-import is allowed; there is no persistent backup-level dedupe requirement.

Replace

  • Replace the complete task-owned persistent graph as defined by the app contract.
  • Do not equate “replace tasks” with “replace all settings/runtime/security state”.
  • AlarmManager registrations are derived and are reconciled separately from persistence.

Settings

  • Matching portable fields use their field-specific import policy.
  • Omitted fields remain local.
  • Runtime/device-local fields are not activated from the file.

19. External .focusflow opening from Android

The documentation must explain that a .focusflow file can be opened directly from a file manager/provider.

File Manager / Drive
      ↓
ACTION_VIEW
      ↓
FocusFlow receives URI
      ↓
read content
      ↓
validate/normalize
      ↓
PendingImport snapshot
      ↓
ImportConfirmScreen

Required lifecycle coverage for the implementation:

  • cold start
  • warm start / onNewIntent
  • repeated delivery of the same URI
  • two different files arriving rapidly
  • cancellation and re-open
  • provider read failure / disappearance
  • content:// handling
  • deterministic file:// behavior

Filename/MIME do not override a valid FocusFlow envelope once the file is delivered to the app. Conversely, a valid JSON file should not magically become discoverable as a handler solely because its content looks right; Android intent-filter/provider behavior controls discoverability.

20. Export semantics

Canonical export content:

  • portable settings according to the V1 list above
  • all task records
  • descriptive presetSections
  • summary counts
  • exportedAt / display metadata

The exporter should canonicalize task timestamps to UTC Z.

Suggested output filename:

focusflow-2026-09-01T14-30-00.focusflow

The current Android transport uses SAF ACTION_CREATE_DOCUMENT and writes application/octet-stream to the chosen document URI.

24. Agent-facing “do not make these mistakes” section

  • Do not turn .focusflow into a ZIP, SQLite dump, or binary database backup.
  • Do not use Kotlin internal property names such as allowedFocusPackages in the public V1 wire format; use allowedInFocus.
  • Do not encode reminders as integer offsets; use reminder objects.
  • Do not use presetSections as live activation instructions.
  • Do not serialize the current active focus session as if it were portable.
  • Do not treat AlarmManager registrations as persistent backup truth.
  • Do not generate a fake notifId merely to make a reminder object look complete.
  • Do not merge greyoutSchedule and recurringBlockSchedules into one array.
  • Do not use summary as the source of truth.
  • Do not assume a package with the same app label is equivalent to a different package ID.
  • Do not use an empty focusAllowedPackages list casually; it can resolve to block-all behavior.
  • Do not claim that every persisted Reminder object directly schedules an Android notification.
  • Do not silently interpret unsupported/legacy settings as active Kotlin features.
  • Do not claim that importing the file restores live alarms or active blocking sessions verbatim; those are reconstructed/kept local according to the app contract.

28. Important note about “perfectly valid”

A syntactically valid .focusflow is not automatically semantically correct. The HTML should distinguish:

FORMAT VALID
    JSON/schema/limits are valid

IMPORT SAFE
    content will not trigger malformed/unsupported restore behavior

PRODUCT SEMANTICALLY CORRECT
    fields represent the intended FocusFlow behavior

The goal of the documentation and builder is the third level, not merely the first.
