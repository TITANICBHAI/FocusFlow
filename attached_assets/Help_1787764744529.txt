Persistence map / ownership
All native components use one focusday_prefs file (AppBlockerAccessibilityService.kt:73-98; SharedPrefsModule.kt:37-39; widget FocusFlowWidget.kt:70-74). Native writers/readers include SharedPrefsModule, NetworkBlockModule, GreyoutModule, AversionsModule, AppBlockerAccessibilityService, ForegroundTaskService, BootReceiver, PackageInstallReceiver, BlockOverlayActivity, TemptationLogManager, VpnWatchdogReceiver, VpnRecoveryNotifier, NotificationActionReceiver, FocusDayBridgeModule, widget, launcher/admin receivers.
Focus state: focus_active, allowed_packages, task fields (task_id, task_name, task_start_ms, task_end_ms, task_duration_ms, task_last_written_ms, next_task_name, task_color), break fields. JS orchestration writes these via multiple bridge calls (focusService.ts:51-79, stop at :102-107); Kotlin writers are SharedPrefsModule.kt:52-66,105-110,123-151 and service start writes task_start_ms at ForegroundTaskService.kt:621-646.
Standalone state is a three-key tuple (standalone_block_active, standalone_blocked_packages, standalone_block_until_ms) written in one editor (SharedPrefsModule.kt:251-279) and read by Accessibility, Foreground, Boot, VPN, widget. Always-on is similarly always_block_active + always_block_packages (SharedPrefsModule.kt:297-304; constants AppBlockerAccessibilityService.kt:141-142).
Allowance config is rich JSON daily_allowance_config; legacy daily_allowance_packages remains read as fallback but is explicitly “no longer written” (AppBlockerAccessibilityService.kt:95-106,2452-2493). Usage and reconciliation are JSON objects in daily_allowance_used, daily_allowance_usage_stats_sync, plus four active-session marker keys (:2383-2408).
VPN has duplicate/legacy gates and lists: net_block_enabled + net_block_vpn; vpn_selected_packages + canonical net_block_packages; net_block_mode, net_block_global, Wi-Fi/mobile/restore/self-heal, status/error/failure/permission flags. Duplication is deliberately synchronized in some paths (SharedPrefsModule.kt:395-421) but not globally guaranteed (NetworkBlockModule.kt:186-200).
Overlay config is generic/untyped (BlockOverlayModule.kt:80-184) and escape handshake uses overlay_x_ready, current_foreground_pkg, current_foreground_cls, overlay_escape_attempts (BlockOverlayActivity.kt:153-175,238-258,561-601). Generic SharedPrefsModule.putString permits arbitrary key collisions (SharedPrefsModule.kt:444-480).
Widget reads task/standalone/next-upcoming/stats keys (FocusFlowWidget.kt:165-203). Task fields are typed, but task_awaiting_decision, next_upcoming_start_ms are strings (:175,178-180), while timestamps elsewhere are Longs. JS updates these independently (AppContext.tsx:920-951).
Concrete failure modes
Non-atomic focus start / bridge timing: startFocusMode starts the foreground service before writing focus_active, task snapshot, and allowed packages (focusService.ts:57-79). Native service can render active notification and accessibility can observe a partially updated tuple. The four subsequent bridge promises are sequential but each is a separate apply(). A kill/crash between calls can leave focus_active=true with old/missing allowlist, stale task metadata, or vice versa. Conversely service starts before native enforcement state exists. Stop has the same split-brain risk (focusService.ts:102-107), and ForegroundTaskService itself can clear focus_active (:1119-1124) before later JS cleanup.
Cross-component state race: receivers and services rebuild JSON by read/modify/write. PackageInstallReceiver reads runtime_install_flagged and standalone package JSON, then writes after both mutations (PackageInstallReceiver.kt:76-114); simultaneous install/accessibility/JS writes can lose updates. Allowance read-modify-write is repeated in recordAllowanceOpen, accumulateTimedUsage, reconciliation, and reset (AppBlockerAccessibilityService.kt:2534-2577,2590-2637; SharedPrefsModule.kt:613-627) with no process-wide lock/transaction. Two foreground events or a UsageStats sync can overwrite increments.
apply() durability: every critical native write uses asynchronous .apply() rather than .commit() (examples SharedPrefsModule.kt:65,84,109,148; temptation TemptationLogManager.kt:38-59; VPN status NetworkBlockerVpnService.kt:136-145). apply() updates in-memory state quickly but disk flush is deferred; abrupt power loss immediately after a focus/standalone/VPN change can reboot into stale enforcement. BootReceiver itself clears expiry with apply() (BootReceiver.kt:70-74) and may then start a service based on a pre-flush snapshot.
JSON corruption silently changes enforcement: most parsers catch exceptions and substitute empty arrays/objects. Temptation log corruption becomes an empty log (TemptationLogManager.kt:40-42), widget corruption displays zero blocked apps (FocusFlowWidget.kt:128-130), package/allowlist corruption becomes empty sets (ForegroundTaskService.kt:1187-1203; AppBlockerAccessibilityService.kt:2676-2683,2483-2493). Depending on mode, malformed allowed_packages can block every app or fallback can disagree with Accessibility. Rich config corruption falls back to legacy (AppBlockerAccessibilityService.kt:2478-2493), potentially unexpectedly re-enabling old allowances.
Key ownership/inconsistency: comments claim daily_allowance_packages but JS now writes daily_allowance_config; old callers can silently diverge. VPN has two gates/lists (net_block_enabled vs net_block_vpn, vpn_selected_packages vs net_block_packages). Widget uses next_upcoming_*, while Boot/service restore uses next_task_name (FocusFlowWidget.kt:177-180; BootReceiver.kt:78-86; ForegroundTaskService.kt:666-688). This produces a widget that says “next up” while rebooted notification has no next task. Task awaiting state is only a JS generic-key write and is not cleared atomically with task fields (AppContext.tsx:920-951).
Expiry/restart semantics: Boot validates focus using task_end_ms and an unusual secondary duration check (BootReceiver.kt:47-68), but only restarts active service when endTimeMs > 0; a secondary-valid clock-tamper case with expired endTimeMs does not enter active restore (:76). Foreground sticky restart restores only on intent == null (ForegroundTaskService.kt:661-703); Android/OEM restart intent behavior can vary. In-memory isRunning is process-local and resets false (NetworkBlockerVpnService.kt:109-110), so watchdog/accessibility can race duplicate starts. Alarm schedules are not persisted/rearmed universally: watchdog is rearmed by Boot only for focus + self-heal (BootReceiver.kt:90-97), although VPN persistence can be standalone/always-on; weekly temptation alarm is scheduled only when settings flow invokes it (TemptationLogManager.kt:113-147) and is not restored on boot/package replacement.
Cross-process consistency: all components use ordinary MODE_PRIVATE SharedPreferences, not a transactional cross-process store. Receivers can launch a fresh app process (VpnWatchdogReceiver.kt:24-27), while services may be alive in another process instance. Android SharedPreferences is not a supported multiprocess synchronization mechanism; cached maps can be stale and concurrent read/modify/write can lose data. apply() further widens this window. No android:process is specified in the manifest reference, but fresh-process delivery after process death still matters.
Notification bridge loss/duplication: NotificationActionReceiver persists a 4-key action tuple then launches MainActivity and broadcasts (NotificationActionReceiver.kt:43-74). Bridge clears the tuple on immediate handling (FocusDayBridgeModule.kt:72-97) or clears it before validating age/event delivery on resume (:138-188). If JS dies between clear and emit, action is lost. Only one pending action is supported; rapid taps overwrite earlier actions. Immediate broadcast is discarded if no active React instance (:72), relying on the tuple. TASK_ENDED/APP_BLOCKED broadcasts are simply dropped when JS is dead (FocusDayBridgeModule.kt:211-220); only native enforcement continues.
Native feature coverage when JS is dead: app blocking, fallback polling, overlay, aversive actions, allowance timers/checkpoints, VPN restart/watchdog, Boot restore, package-install handling, widget refresh, and weekly temptation notification are native. But task action completion/extend/skip ultimately depends on JS bridge; no native DB mutation occurs. Pending notification replay expires after five minutes and can be lost. JS-only DB state (task schedule, settings, reports) cannot be recovered by native services beyond mirrored snapshot fields. ForegroundTaskService explicitly says Accessibility owns allowance accounting (:1173-1177), so a dead Accessibility service leaves only fallback blocking, not equivalent allowance behavior.
Overlay timing/race: Accessibility raises overlay and sets a readiness flag; activity polls every 300ms and clears it (BlockOverlayActivity.kt:38-53,153-158,588-601). Multiple blocked-app events can overwrite current foreground/quote/readiness; stale activity can re-raise based on changing prefs. This is a transient handshake, not an atomic request queue.
VPN lifecycle: NetworkBlockerVpnService restores from prefs on sticky restart (:156-186) and watchdog uses persisted canonical list (VpnWatchdogReceiver.kt:103-177), which is good, but permission loss writes flags asynchronously and recovery can post repeatedly. VPN package JSON is passed in intents while also read from prefs; differing snapshots can start the tunnel with one list and watchdog later rebuild with another. NetworkBlockModule.startNetworkBlock persists list/mode before asynchronous service dispatch (NetworkBlockModule.kt:255-290), but settings updates can race that dispatch.
SQLite/database findings
JS uses Expo SQLite focusday.db with a recovery DB (src/data/database.ts:1-9), serialized writes (:20-27,86-93), dead-handle retry and recovery DB (:65-80,137-155,199-280), and task/focus-session tables (:414-439,684-706). There are no native Kotlin SQLite/Room/DataStore references; native enforcement is entirely SharedPreferences.
SQLite improves durable/history-heavy data (tasks, schedules, completed focus sessions, reports, temptation history) and gives transactional multi-row updates, but Room alone would not solve the native service snapshot problem: Accessibility/VPN/receivers need a tiny fast, boot-readable, native-owned state and must not depend on the JS bridge/Expo DB being initialized. Introducing Room would also add migration/opening lifecycle complexity and, unless every native component shares the same DB access/locking contract, simply create a second source of truth.
Keep in SharedPreferences or migrate the small native contract to Preferences/DataStore: active enforcement mode, allow/block lists, expiry/start timestamps, VPN configuration/status, protection flags/PIN hashes, overlay handshake, pending native notification action, and compact allowance checkpoint/heartbeat. Prefer one versioned serialized snapshot (or DataStore transaction) for each state tuple, with schema/version/checksum and explicit corruption handling. DataStore is not a drop-in cross-process fix: use a supported multi-process design or a native SQLite/Room repository if components truly run in separate processes; ordinary SharedPreferences is currently unsafe for that guarantee.
Move append-heavy temptation logs and rich allowance/history into SQLite/Room (with atomic upsert/transactions), while mirroring only the active allowance counter/checkpoint needed for JS-dead enforcement. Keep widget daily stats and current task snapshot in the native store. The JS DB remains the source for rich UI/task history, but all native-critical state needs a single native owner and an atomic commit protocol.

Audit scope: artifacts/focusflow JS/TS + Android native persistence/enforcement.

Persistence topology / ownership
Primary task/settings DB is Expo SQLite focusday.db; focusday_recovery.db is an empty fallback. Schema/tables and singleton/open/write queue are src/data/database.ts:1-39,59-93,137-179,199-284,351-452. Tables: tasks, settings (one JSON blob), focus_sessions, focus_overrides, daily_completions; indexes at data/database.ts:376-452.
React useReducer is the live UI cache, not durable state: src/context/AppContext.tsx:76-133. It holds today + recent unresolved tasks, settings, focus session, loading/DB flags. Derived active/current/task lists are only in-memory (AppContext.tsx:1895-1900).
Android SharedPrefs is a second, native enforcement/runtime store. JS wrapper silently no-ops absent methods and catches native errors (src/native-modules/SharedPrefsModule.ts:16-39,41-80,135-165,266-290); Kotlin uses separate SharedPreferences.Editor.apply() writes (android-native/.../SharedPrefsModule.kt:37-67,100-110,123-151,251-279,297-305,437-460). Accessibility/boot/foreground services consume those values without JS.
AsyncStorage is only setup-marker redundancy (src/services/setupPersistence.ts:1-15,26-45,48-96), logger storage (src/services/startupLogger.ts:23-27,81-120), and dismissible help hints (app/(tabs)/focus.tsx:31-34,90-103, app/(tabs)/defense.tsx:29,59-81,992-1010, app/block-defense.tsx:44,992-1010). It is not the task/settings source of truth.
Concrete data-loss/corruption/fallback risks
Recovery DB silently loses all existing data. After primary open/init fails twice, code opens fresh focusday_recovery.db and returns it as if normal (data/database.ts:183-188,211-275). No user-visible recovery/import is forced; subsequent writes go to the fresh DB, while the primary may still contain the user data. A later process can reopen primary, making recovery-written tasks/settings appear to vanish. dbGet* functions intentionally convert all failures to empty/default values (database.ts:456-460,646-669,696-708,711-727,842-865,893-907), so DB-unavailable/corrupt data often renders as a legitimate empty/default state.
Export can produce a valid empty backup after DB failure. buildBackupJson catches dbGetAllTasks and substitutes [] (backupService.ts:233-255), so export succeeds with a backup that can overwrite the user’s only good copy conceptually while silently omitting tasks.
Malformed settings/task JSON degrades silently. Settings parse failure returns DEFAULT_SETTINGS without repairing the DB (database.ts:646-669); malformed task tags, reminders, or focus_allowed_packages become empty arrays (database.ts:613-641), hiding corruption and potentially changing behavior. safeJsonParse validates neither types nor bounds.
Migration catches every ALTER error as “already exists.” ALTER TABLE ... ADD COLUMN focus_allowed_packages is swallowed for any reason (database.ts:436-442), not just duplicate-column; a locked/corrupt/incompatible schema can remain missing the column and later INSERT/UPDATE fails. There is no schema version table, migration transaction, verification, or repair migration.
No foreign keys despite task/session references. Schema explicitly has no FK constraints (database.ts:351-355 comment; tables 408-425), so deleted tasks can leave sessions/overrides orphaned; session/task integrity is application-only.
Partial destructive operations. Delete-task does DB delete, then shifted-task batch update, then reminder cancellation/scheduling (AppContext.tsx:1271-1305); failure after delete leaves DB/state/reminders divergent. Clear-all separately stops session, ends session, cancels reminders, and deletes rows (app/(tabs)/settings.tsx:151-179), with no cross-store transaction. Import replacement deletes each existing task independently and ignores deletion errors (backupService.ts:416-423), then inserts one-by-one (426-455): cancellation/error yields a partially replaced dataset; there is no DB transaction or atomic replace.
INSERT OR IGNORE masks failed/duplicate inserts. dbInsertTask uses INSERT OR IGNORE (database.ts:527-549), but addTask always dispatches the task after the call (AppContext.tsx:1222-1233). Duplicate IDs therefore produce a phantom/duplicate in reducer with no DB row or error. There is no affected-row check.
Update-by-ID does not verify affected rows. dbUpdateTask/batch updates do not check changes; an update for a missing task resolves successfully (database.ts:551-605), while UI assumes persistence.
Settings writes are often explicitly non-fatal. setDailyAllowanceEntries, setBlockedWords, recurring schedules, standalone block, quick block, and combined block catch dbSaveSettings failures, log, dispatch the new value anyway, and continue native sync (AppContext.tsx:1689-1717,1719-1732,1734-1786,1792-1816,1827-1893). This creates in-memory/native-vs-DB divergence that disappears on restart. updateSettings is optimistic, then Promise.all([dbSaveSettings,persistSetupBackups]); any failure throws after the UI has already changed and skips native sync (1644-1680).
No transactional multi-store settings update. SQLite JSON, AsyncStorage setup markers, and many independent SharedPrefs keys are written separately/concurrently (AppContext.tsx:1648-1675; setupPersistence.ts:36-45). Crash/power loss can leave each store at a different version. Kotlin’s multiple .apply() calls make partial native state possible (SharedPrefsModule.kt:65,109,141-150,271-278,300-303,437-441).
Native wrapper creates silent fallbacks. Missing custom native methods return undefined/false/0/empty behavior (SharedPrefsModule.ts:35-39,47-79,151-165,260-290); native exceptions are swallowed by callNative (26-32). Focus can therefore resolve while blocking/allowed-list/widget writes failed. AppContext also catches most sync errors and only logs (AppContext.tsx:466-521,695-786). Expo Go cannot include custom modules (SharedPrefsModule.ts:18-20), but UI remains usable.
Manual JSON construction can corrupt native lists. Kotlin creates JSON arrays by interpolating quoted strings without escaping (SharedPrefsModule.kt:106-109,269-274,298-303,320-324,340-344). A malformed package/blocked-word value containing \ or " makes invalid JSON; service parsing may fall back/disable that enforcement.
Focus session races / stale state
Focus start writes an active DB row, then starts foreground service, requests exemption, optionally sends HOME, then writes SharedPrefs in several steps (src/services/focusService.ts:26-86). If native startup fails after DB insert, no rollback leaves an active session row. Two rapid/manual+auto starts can both pass guards and insert multiple active rows; focus_sessions has no uniqueness constraint (database.ts:408-415), and dbGetActiveFocusSession picks newest only (696-708).
stopFocusMode only ends DB session if module-level focusActive && currentTask was true (focusService.ts:88-115). Cold-start cleanup clears native state but does not close a DB active row; AppContext’s stop adds more best-effort teardown (AppContext.tsx:1601-1640). Multiple active rows can persist.
AppContext auto-start is fire-and-forget and updates reducer only after native completion; repeated task timer/tick/manual calls can overlap (AppContext.tsx:1043-1074). There is no start mutex or DB “claim.”
stateRef updates in an effect (AppContext.tsx:840-845), so event callbacks in the same render window can use an older snapshot. The long-lived tick, notification actions, background callbacks, and user actions can concurrently read/modify the same task.
Notification foreground and headless paths are deliberately split, but a process-state race can still duplicate actions around resume. Background side uses a 5-second de-dupe only in AppContext (AppContext.tsx:1519-1543); headless and foreground do not share an atomic idempotency record.
Background notification COMPLETE uses dbUpdateTask({...task,status:'completed'}) without setting updatedAt (tasks/backgroundTasks.ts:218-230), corrupting stats/timing semantics. It also does not update daily completion rows.
Date/scheduler/background defects
Background handlers use UTC date strings (new Date().toISOString().slice(0,10)) and pass them to dbGetTasksForDate, which converts the argument back through local Date and SQLite localtime (tasks/backgroundTasks.ts:80-82,120-121,218-220; database.ts:510-524). In UTC-negative zones this can select yesterday instead of local today. Same pattern affects overrun and notification action handling.
dbGetTodayFocusMinutes compares started_at >= local-midnight.toISOString() but includes open sessions through now (database.ts:711-727); sessions crossing midnight are counted wholly against the start date and active sessions inflate “today.”
dbGetRecentDayCompletions uses UTC toISOString().slice(0,10) against local-date rows (database.ts:893-905), causing heatmap boundary errors.
Backfill is not atomic with task changes: it reads tasks, then writes derived rows later (database.ts:790-821); completion updates can race it. dbRecordDayCompletion uses INSERT OR REPLACE and swallows errors (769-781).
Scheduler algorithms operate on whatever partial state.tasks is available. deleteTask, complete/skip, and extend derive shifts from the reducer window (AppContext.tsx:1273-1289,1330-1354,1406-1426,1441-1465), not a complete DB transaction/read; older/future rows outside the window can overlap or be omitted. rebalanceAfterOverrun returns critical tasks unchanged while shifting later tasks, potentially introducing overlaps (schedulerEngine.ts:133-188). insertTaskSafe reports no “unresolved same/higher-priority conflict” to caller beyond its returned shifted list (194-250).
Background fetch is best-effort OS-controlled (~15m), and explicitly does not process ended tasks (backgroundTasks.ts:111-179); exact timing depends on native AlarmManager/notifications. Re-arming reminders is not atomic with DB updates and schedule calls can fail after state changes. Registration failures are mostly only console warnings (backgroundTasks.ts:261-299).
Reminder scheduling uses a 450-slot cap and silently drops when budget is exhausted (notificationService.ts:81-83,148-154); native AlarmManager scheduling is fire-and-forget (264-266).
Startup/loading UX
Init waits on channels, permissions, exact-alarm probe, foreground service, DB settings (8s timeout), backups, native syncs, task refresh, overdue recovery, and session restore (AppContext.tsx:335-585). withTimeout returns defaults but does not cancel the underlying DB request (135-148,396-399), so a late DB response can race subsequent operations.
A 12-second watchdog forces isDbReady/loading false even if DB never initialized (AppContext.tsx:218-241). The root splash then fades on isDbReady || !isLoading (app/_layout.tsx:181-249), potentially exposing an empty/default app after failure. Schedule screen has no isDbReady gate and its empty list says “No tasks scheduled” (app/(tabs)/index.tsx:30-40,154-177); users can add/edit before initialization has actually completed. Settings gates with “Loading…” (settings.tsx:55-65).
refreshTasks gets today and recent-unresolved in two independent reads and dispatches the merged result; because DB getters return [] on failure, a transient read can replace valid UI with an empty list without an error (AppContext.tsx:1204-1220).
Stats historical fetch falls back to state.tasks whenever historicalTasks.length === 0, so a legitimate empty history displays the today/recent cache as history (app/(tabs)/stats.tsx:93-120). Its all-time Promise.all has no catch/finally, so a DB/native failure can leave the all-time spinner permanently (stats.tsx:352-387).
AsyncStorage hint reads/writes are fire-and-forget with no error handling (focus.tsx:90-103; defense screens above), so dismissals can silently fail/reappear.
Backup/import behavior and limitations
Envelope is version/kind labeled but parser validates only JSON object, kind, settings object, and tasks array; it does not validate version, task shape, timestamps, enums, or nested settings (backupService.ts:307-331). A task with only id can reach DB insertion and fail/partially import.
Import merges settings via shallow spread (backupService.ts:401-409), so nested future settings objects are replaced wholesale. Existing task IDs are skipped; replacement uses per-row delete and per-row insert with no transaction (411-463). Imported past scheduled tasks are rewritten to skipped (426-446), changing source history. Scheduling failure is warning-only after rows are imported (457-465).
Export intentionally strips live enforcement/session toggles (backupService.ts:97-152) and includes presetSections as descriptive inventory only (155-228); restoreFromJson never applies presetSections. A replacement must preserve the distinction between portable configuration and device-local active enforcement, or explicitly tell users what is not restored.
File-open import is always merge-only, while Settings offers add/replace (app/_layout.tsx:365-467, app/(tabs)/settings.tsx:102-149). URI is marked handled before read/parse succeeds (_layout.tsx:392-409), so a transient read failure prevents retry for that URI during process lifetime. The import host effect depends on full state.tasks/settings, causing listener teardown/recreation on every state update (467).
Screens/features that consume persistence
Schedule (app/(tabs)/index.tsx) reads reducer todayTasks and performs add/update/delete/complete/skip/extend/focus; it has active/time-up actions and no DB-ready empty-state gate (30-40,100-229).
Focus (app/(tabs)/focus.tsx) consumes current task/session, timer, Pomodoro break state, emergency override DB log, standalone block, allowed apps, and AsyncStorage hint (36-113,415-535).
Stats (app/(tabs)/stats.tsx) directly queries sessions/overrides/streak/day completions/historical tasks and native temptation logs (stats.tsx:23-41,88-134,279-387).
Settings (app/(tabs)/settings.tsx) directly clears DB, exports/imports, updates settings, permissions and SharedPrefs allowed list (40-207). Other routes (active.tsx, always-on.tsx, block-defense.tsx, keyword-blocker.tsx, home-launcher.tsx, permissions.tsx, user-profile.tsx, vpn-block-list.tsx) mutate settings through AppContext; modals write SharedPrefs for overlay, pins, blocked words, allowance, schedules (src/components/OverlayAppearanceModal.tsx:27-55, PinSetupModal.tsx:38-97, DailyAllowanceModal.tsx:18-23,102-178, GreyoutScheduleModal.tsx:23-71).
Replacement requirements
Durable, single source of truth for settings, tasks, task history, reminders metadata, focus sessions, overrides, daily completions, recurring schedules, allowance rules, blocked words, presets, profile, launcher/VPN/defense configuration; schema versioning, migrations with verification, corruption detection/repair, and transactional writes.
Atomic/idempotent task commands (create/update/delete/status/extend/skip/complete), affected-row checks, unique IDs, conflict-safe schedule rebalance, complete-schedule reads, and a mutation queue/optimistic concurrency version to prevent stale reducer/background/notification writes.
Explicit session lifecycle invariants: at most one active session per task/device, start claim, native-start rollback, cold-start reconciliation of DB vs native state, idempotent notification actions, and durable event/action IDs.
Separate durable user data from device-local enforcement/runtime (SharedPrefs/native service), but provide transactional/versioned synchronization, acknowledgements/health status, retry/backoff, and visible failures instead of undefined/empty silent fallbacks. Native list serialization must use a real JSON encoder.
Headless/background-safe APIs: database open/close/recovery, local-calendar date queries, exact alarms/notifications, background fetch, boot restart, overrun/rearm, and reconciliation when OS kills/restarts JS. Must not rely on in-memory reducer/context.
Backup/export must fail loudly if the canonical DB cannot be read; use a versioned, strongly validated envelope, schema migration/import preview, atomic replace (or journaled staged restore), duplicate policy, full warning/result reporting, and clearly document portable vs device-local live state. Include all supported settings/presets/profile/task/session/history data required by product policy.
Startup must expose DB readiness/error/recovery state separately from loading, block mutations until ready, never show “No tasks” for unknown data, recover from timeout without abandoning the in-flight operation, and provide retry/recovery/import UX. Screens should use query states (loading/empty/error/stale), not infer empty from [].
Stats/analytics requirements include correct local-day boundaries, historical/all-time task queries, focus duration/session counts, overrides/temptation logs, streak/backfill, heatmap, and cancellation/error handling for every fetch; derived daily rows should be transactionally maintained or safely recomputed.
Preserve all current feature data: task title/description/times/duration/status/priority/tags/reminders/color/focus flag/per-task allow-list; global allowed apps, Pomodoro, reminder/notification preferences; standalone + always-on app/VPN lists and expiry/auto-copy; daily allowance count/time-budget/interval parameters and usage reset; blocked words; aversion flags; weekly/morning reports; greyout and recurring schedules including VPN fields; system/content guards; defense PIN/protection mode; launcher hidden/pinned/dock/wallpaper/clock/lock/uninstall; profile/chronotype/goals/preferences; pending achievements/tips; widget active-task/stats snapshot; and portable backup/import semantics.
