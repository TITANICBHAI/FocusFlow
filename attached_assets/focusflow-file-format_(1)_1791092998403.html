FocusFlow .focusflow — Complete V1 File Format Reference

0. Purpose

This document is the content and behavior master specification for every public HTML page that documents, generates, validates, edits, or explains a FocusFlow .focusflow file.

The goal is stronger than “explain the format.” An implementation agent that receives the finished HTML pages, without access to the source repository, must have enough information to:

  • understand exactly what a V1 .focusflow file is;
  • generate a valid canonical V1 file;
  • generate a useful full backup containing all portable V1 settings and task data;
  • validate hand-written files before download;
  • understand which fields are portable, ignored, device-local, runtime, derived, or informational;
  • preserve the important three-way semantics of fields such as focusAllowedPackages;
  • generate task, reminder, preset, allowance, recurring-schedule, greyout, and profile objects correctly;
  • understand how FocusFlow will normalize, ignore, reject, skip, merge, or replace data during import;
  • avoid reproducing old TypeScript/Kotlin bugs or stale documentation claims;
  • distinguish the actual .focusflow wire format from Android runtime behavior that is not serialized in the file.

This document is intended to be the authoritative source for the HTML content. It is not itself the Kotlin implementation contract, although it incorporates the file-format portions of the final FocusFlow V1 implementation contract.

1. Source hierarchy and truth model

1.1 Sources used

The current content must be based on these supplied materials:

  1. Final FocusFlow backup/import/alarm implementation contract (FocusFlow_Implementation_Plan_FINAL v14.md).
  2. Current Kotlin source archive containing the backup exporter, parser, limits, settings adapter, task model, alarm/repository code, and related persistence code.
  3. Current .focusflow documentation HTML supplied with the project.
  4. Current .focusflow backup builder HTML supplied with the project.

The current HTML pages are not automatically authoritative. They are the thing being improved and currently contain stale or misleading claims.

1.2 Evidence labels for documentation authors

When a statement is particularly implementation-specific, the source should be treated using these categories:

  • [TS] — verified legacy TypeScript behavior recorded in the final implementation contract.
  • [KT] — verified in the current Kotlin archive.
  • [CONTRACT] — explicit final V1 product/implementation decision.
  • [DOC] — Android documentation/platform requirement.
  • [DEVICE] — behavior that must be experimentally verified on a real device.
  • [INFERENCE] — derived explanation rather than a directly serialized field rule.

Public HTML does not have to show these tags everywhere, but the content author must use them to avoid presenting an inference as a schema fact.

1.3 Three-way truth model

Always keep these three concepts separate:

Observed legacy TS behavior
        ↓
Intended FocusFlow product semantics
        ↓
Current/final Kotlin V1 behavior

A legacy bug is not automatically part of the V1 specification.

Also keep these four file concepts separate:

WIRE COMPATIBILITY
    What JSON names/shapes a V1 reader accepts.

PORTABILITY
    What state is actually meaningful to move between devices.

APPLICATION
    What imported data is allowed to change on the destination device.

RUNTIME / DERIVED STATE
    What must be recreated by the Android app rather than serialized.

A field can be accepted for compatibility while being intentionally ignored during application.

2. What a .focusflow file is

A .focusflow file is a plain UTF-8 JSON document using the .focusflow filename extension.

It is not a ZIP archive and does not contain an internal directory structure.

Canonical file properties:

  • extension: .focusflow;
  • content: JSON text;
  • encoding: UTF-8;
  • V1 envelope identity: kind = "FocusFlowBackupV1";
  • V1 version: 1;
  • main persistent payload: settings + tasks;
  • presetSections and summary are informational/inventory metadata, not authoritative live state;
  • Android alarm registrations, notifications, current focus sessions, PIN state, live blocking state, permissions, and other runtime/derived state are not portable file state.

Do not describe .focusflow as “a complete database dump” or “the entire device state.” It is a versioned portable representation of selected FocusFlow state.

3. Filename and extension

3.1 Extension

The canonical filename ends in:

.focusflow

Example:

focusflow-2026-10-04T10-44-00.focusflow

The filename is a discovery/convenience mechanism. The JSON envelope is the authoritative format identity.

3.2 File content does not depend on filename

The importer validates the content envelope. A file being named .focusflow does not make invalid JSON valid.

Likewise, a valid V1 JSON document can be recognized by content even if a file provider gives it an unexpected MIME type; the application has explicit content validation.

3.3 File-provider handling

The Android app can receive the file through:

  • the in-app document picker (ACTION_OPEN_DOCUMENT);
  • an external ACTION_VIEW document flow from a file manager/provider.

The HTML documentation should explain the file itself, not imply that a particular file manager or MIME type is part of the JSON schema.

4. Encoding and JSON syntax rules

4.1 UTF-8

The V1 parser expects valid UTF-8.

Malformed UTF-8 is a file-level rejection.

The parser uses strict UTF-8 decoding rather than silently replacing invalid bytes.

4.2 BOM

A leading UTF-8 BOM is stripped before JSON parsing.

For a canonical generator, simply emit normal UTF-8 JSON without a BOM unless there is a specific reason not to.

4.3 JSON syntax

The document is standard JSON:

  • no comments;
  • no trailing commas;
  • property names are quoted strings;
  • strings use normal JSON escaping;
  • JSON booleans are true / false;
  • JSON null is null;
  • numeric fields must be JSON numbers, not numeric strings, unless a field is explicitly defined as a string.

4.4 Duplicate JSON keys

Duplicate object keys are rejected at any depth.

This includes duplicates that appear equivalent after JSON escaping, such as escaped spellings that decode to the same key.

HTML builders must therefore never emit duplicate properties in a JSON object.

4.5 Unknown fields

V1 readers tolerate unknown optional fields in compatible JSON objects.

Unknown fields are not automatically applied and there is no promise that arbitrary unknown fields survive a future export.

This means the HTML documentation should not say:

“Every key in the file is required.”

Instead, it should distinguish:

required structural fields
recognized portable fields
ignored legacy/device-local fields
unknown tolerated fields

5. Top-level V1 envelope

5.1 Required structural fields

The top-level JSON object must contain:

{
  "kind": "FocusFlowBackupV1",
  "settings": {},
  "tasks": []
}

version is strongly recommended and is emitted by the exporter, but the V1 parser accepts a missing version and interprets it as version 1.

5.2 Exact top-level field reference

Field Type Required for acceptance Canonical meaning
kind string YES Must equal exactly FocusFlowBackupV1.
version integer NO 1 for V1. If present and not 1, reject the file. If absent, treat as 1.
exportedAt string NO Export timestamp; canonical form is UTC .sssZ. Informational metadata.
exportedAtHuman string NO Human-readable export timestamp. Informational only.
appVersion string NO Source app version metadata. Not a schema/version compatibility selector.
platform object NO Platform metadata. Current exporter uses { "os": "android" }. Informational only.
settings object YES Recognized portable settings payload.
tasks array YES Task records.
presetSections array NO Export inventory/summary sections. Never authoritative for live application.
summary object NO Informational counts. Never authoritative.
unknown top-level keys any valid JSON value tolerated Must not be assumed to be portable or applied.

5.3 Top-level version rules

version absent → interpret as 1
version = 1    → accept as V1
version ≠ 1    → reject file before mutation

Do not present this as “version 1 is always mandatory.” It is canonical output, but omission is accepted input.

5.4 Minimum valid starter

Canonical minimal file:

{
  "kind": "FocusFlowBackupV1",
  "version": 1,
  "settings": {},
  "tasks": []
}

The current HTML must use this as the minimum example.

6. Top-level metadata semantics

6.1 exportedAt

Canonical exporter representation:

YYYY-MM-DDTHH:mm:ss.SSSZ

Example:

2026-10-04T05:14:00.000Z

It is metadata. It does not control restore time.

6.2 exportedAtHuman

Human-readable metadata generated for display.

Current exporter uses a localized/human-readable value such as:

04/10/2026, 10:44:00

The importer does not use this field as an authoritative timestamp.

A builder should generally generate it for a pleasant full example but should never derive scheduling semantics from it.

6.3 appVersion

Optional string containing the originating app version.

It is useful for diagnostics and migration analysis.

It is not the schema version.

6.4 platform

Current canonical platform payload:

{
  "os": "android"
}

It is informational.

Do not use the platform field to decide whether tasks are valid or whether settings are portable.

6.5 summary

Current exporter emits:

{
  "taskCount": 0,
  "blockedWordCount": 0,
  "greyoutWindowCount": 0,
  "dailyAllowanceCount": 0
}

These values are informational only.

The importer does not trust them as the source of truth.

The builder should calculate accurate values for human usefulness, but a mismatch is not the same thing as corrupt primary data.

Do not repeat the old HTML claim that summary.taskCount is authoritative or that a mismatch itself necessarily causes import failure.

The authoritative task count is tasks.length.

8. Task object — canonical V1 schema

Each element of tasks is a Task record.

Canonical task structure:

{
  "id": "MPzb6gCgQWmRJH3RuhTPE",
  "title": "Plan the week",
  "description": "Choose the three most important tasks.",
  "startTime": "2026-10-05T04:00:00.000Z",
  "endTime": "2026-10-05T05:00:00.000Z",
  "createdAt": "2026-10-04T05:00:00.000Z",
  "updatedAt": "2026-10-04T05:00:00.000Z",
  "durationMinutes": 60,
  "status": "scheduled",
  "priority": "medium",
  "tags": ["planning"],
  "reminders": [],
  "color": "#6366f1",
  "focusMode": false,
  "focusAllowedPackages": null
}

title string required; non-blank Display title. Max 1,000 chars.
description string or null canonical generator should use string Missing/null becomes "". Max 20,000 chars.
startTime string required ISO-8601 date-time with Z or offset; normalized to UTC .sssZ.
endTime string required ISO-8601 date-time with Z or offset; must not be earlier than startTime; normalized to UTC .sssZ.
createdAt string required ISO-8601 date-time with Z or offset; normalized to UTC .sssZ.
updatedAt string required ISO-8601 date-time with Z or offset; normalized to UTC .sssZ.
durationMinutes integer required Must be an integer in 0..100000.
status string required One of scheduled, active, completed, skipped, overdue.
priority string required One of low, medium, high, critical.
tags array of strings canonical generator should emit array Max 100 entries; each max 100 chars. Missing means empty list.
reminders array canonical generator should emit array Preserve as inert task data. Invalid reminder items are dropped with warnings rather than invalidating the whole task.
color string optional Max 32 chars. Missing → #6366f1. V1 parser does not require a particular hex syntax.
focusMode boolean optional Missing → false.
focusAllowedPackages array, null, or omitted optional Three-way semantics; see §10.

8.2 Task IDs

The current TS data commonly uses nanoid-style IDs around 21 characters from:

[A-Za-z0-9_-]

For new files generated by the HTML builder, prefer the same style:

~21 URL-safe characters
A-Z / a-z / 0-9 / _ / -

The V1 parser's actual acceptance rule is broader:

1–128 characters
no control characters

Do not artificially reject a valid imported ID merely because it is not exactly 21 characters.

8.3 Uniqueness

Task IDs must be unique within a generated file.

Duplicate task IDs inside the incoming file are a whole-file rejection, before any restore mutation.

This is a deliberate V1 safety rule even though the legacy TS database loop could silently ignore repeats.

8.4 Title

title must be:

  • a JSON string;
  • non-blank after validation;
  • at most 1,000 characters.

The builder should visibly mark an empty title as invalid.

8.5 Description

description can be an ordinary string.

The importer also accepts null or absence and normalizes these to:

"description": ""

For canonical generated files, use a string consistently.

8.6 Time ordering

The parser requires:

endTime >= startTime

It does not state a separate file-level requirement that the difference must exactly equal durationMinutes.

For a generated file, the builder should nevertheless make the data internally coherent:

durationMinutes
= exact whole-minute difference between endTime and startTime

This is a canonical generation invariant, not a claim that a mismatch is necessarily a V1 parser rejection.

8.7 Zero-duration tasks

The current V1 parser permits:

durationMinutes = 0

and only constrains it to 0..100000.

For normal generated scheduling examples, prefer a positive duration unless the user explicitly wants an instantaneous/zero-duration task.

9. Timestamps and UTC

9.1 Canonical timestamp representation

All four task timestamps should be emitted as:

YYYY-MM-DDTHH:mm:ss.SSSZ

Example:

2026-10-04T05:14:37.125Z

Canonical formatting is always UTC.

9.2 Accepted input

The importer accepts ISO-8601 timestamps containing:

  • Z; or
  • an explicit UTC offset such as +05:30 or -04:00.

They are normalized to canonical UTC .sssZ before storage.

Example:

2026-10-04T10:44:00+05:30

normalizes to:

2026-10-04T05:14:00.000Z

9.3 HTML guidance

The documentation should explain both:

DISPLAY TIME → device local time
WIRE TIME    → UTC

There is no task-timezone field in the V1 task schema.

9.4 India / IST example

IST is UTC+05:30.

07:00 IST → 01:30Z
10:00 IST → 04:30Z
13:00 IST → 07:30Z
22:30 IST → 17:00Z
23:30 IST → 18:00Z

When generating a .focusflow task for a specified local time, convert the intended local instant to UTC rather than manually copying the local clock value into the file.

9.5 Do not compare timestamps as arbitrary strings

Internal software should compare parsed time values (Instant/epoch semantics), not rely on unnormalized timestamp string ordering.

The canonical HTML should teach file authors to emit normalized .sssZ values.

10. focusAllowedPackages — critical three-way semantics

This is one of the most important parts of the .focusflow format.

There are three distinct states:

State A — omitted

{
  "focusMode": true
}

Meaning:

Use the global FocusFlow setting `allowedInFocus`.

State B — explicit null

{
  "focusMode": true,
  "focusAllowedPackages": null
}

Meaning in the Kotlin/TS model:

Use the global FocusFlow setting `allowedInFocus`.

The V1 model preserves the distinction between wire presence and value, even though both omitted and explicit null resolve to the global allow-list at runtime.

State C — explicit array

{
  "focusMode": true,
  "focusAllowedPackages": [
    "com.example.reader",
    "com.example.notes"
  ]
}

Meaning:

Use this task-specific package allow-list.

State D — explicit empty array

{
  "focusMode": true,
  "focusAllowedPackages": []
}

Meaning in the current model:

All apps are allowed for this task's focus session.

This is not the same as null.

It is also not the legacy preset block-all sentinel.

10.1 Crucial warning for the HTML builder

Do not tell users:

focusAllowedPackages: [] → block all apps

That is incorrect for Task records.

The special sentinel concept appears in allowed presets and is separate from the task-level focusAllowedPackages semantics.

10.2 Package validation

Canonical package names must match:

^[A-Za-z][A-Za-z0-9_]*(\.[A-Za-z0-9_]+)+$

Maximum package-name length:

255 characters

Maximum list size:

5,000 entries

Invalid package entries are dropped with warnings by V1 normalization rather than necessarily invalidating the whole task/list.

For generated files, never generate invalid package identifiers.

11. Task status semantics

V1 recognizes five status values:

scheduled
active
completed
skipped
overdue

11.1 Imported scheduled

If the task's end time is still in the future at the captured restore planning time:

scheduled → scheduled

If the end time has already passed:

scheduled → skipped

and:

updatedAt = planNow

The import-time downgrade is intentional: it treats an already-finished scheduled task as closed historical work rather than something the new device should immediately schedule.

11.2 Imported active

active represents runtime state of the source device and is not restored as a live focus session.

V1 import handling:

active + future end → scheduled
active + past end   → skipped

Never resurrect a source device's live session merely because a task was marked active in the file.

11.3 Imported completed

Preserve as:

completed

No task-end alarm should be recreated for it.

11.4 Imported skipped

Preserve as:

skipped

No task-end alarm should be recreated.

11.5 Imported overdue

Preserve as:

overdue

No task-end alarm should be recreated.

11.6 Local overdue sweep vs import downgrade

These are intentionally different:

IMPORT:
old scheduled/active task → skipped

NORMAL LOCAL STARTUP SWEEP:
unfinished scheduled/active task whose endTime has passed → overdue

The HTML must not conflate these states.

12. Task priority

Valid values:

low
medium
high
critical

Priority is semantic task data and is included in duplicate-task comparison.

The color assigned to a task is independent from priority.

13. Tags

tags is an array of strings.

Canonical generated examples:

"tags": []

or:

"tags": ["biology", "revision"]

V1 limits:

  • maximum 100 tags per task;
  • maximum 100 characters per tag.

The current parser does not require tags to be unique. A generator may deduplicate them because tags are treated as set-like semantic data in canonical duplicate comparison, but this should be described as canonicalization rather than a schema requirement.

14. Task.reminders[] — persistent but inert in scheduling

14.1 Reminder object

Canonical reminder shape:

{
  "id": "reminder-001",
  "taskId": "task-001",
  "offsetMinutes": -5,
  "type": "pre-start"
}

Supported fields:

Field Type Rule
id string non-blank, max 128 chars
taskId string non-blank, max 128 chars; canonical generator should equal the parent task ID
offsetMinutes integer JSON integer; negative is before start, positive is after start according to the model
type string pre-start, at-start, post-start
notifId string or null optional; max 128 chars if present

Maximum reminders per task:

100

14.2 Current real-world usage

Legacy TS initializes Task.reminders to [] and did not populate it through its normal task creation paths.

The V1 contract therefore treats the array as persistent task data that should be preserved opaquely.

14.3 Scheduling rule

Never generate or schedule Android reminder alarms from Task.reminders[].

Current task-relative notification behavior is derived from the task's:

id
startTime
endTime
status

The HTML must explicitly teach this distinction because otherwise a future builder might generate a logically valid reminder array and incorrectly assume that the Android scheduler will use it.

14.4 Invalid reminder items

Malformed reminder entries are dropped with warnings rather than invalidating the whole task.

If the entire reminders field is not an array, V1 normalization replaces it with an empty list and records a warning.

A canonical builder should simply always emit a valid array.

15. Task color

The current V1 parser requires only:

string
length ≤ 32 characters

Missing color becomes:

#6366f1

The parser does not impose a strict hex-color grammar in the current source.

Therefore:

  • hex values such as #6366f1 are the recommended user-facing form;
  • the HTML should present palettes as examples, not as the complete allowed-value set;
  • the HTML must not claim that a specific priority automatically determines the color.

The old color palette can remain as a visual convenience, but must be labeled “common examples” rather than “the valid color codes.”

16. Task focusMode

focusMode is boolean.

Missing value:

false

Typical generated examples:

"focusMode": true

or:

"focusMode": false

The important related field is focusAllowedPackages (§10).

focusMode itself does not encode the currently active Focus Session.

17. Task unknown fields

A V1 task may contain additional object properties unknown to the current importer.

The parser's normalized task retains the original object and rewrites recognized fields into canonical form.

The HTML should therefore say:

Unknown task fields may be tolerated in V1.
Do not rely on unknown fields being portable or preserved by future exports.

For the builder, do not create arbitrary custom properties unless the user explicitly wants a compatibility experiment.

18.1 Settings omission semantics

For APPLY fields:

key present + valid → overwrite destination value
key absent         → leave destination value unchanged

Settings are not a blanket object replacement; each recognized field has its own application policy.

18.2 Collections are overwritten wholesale

For recognized portable arrays/collections, the import contract is:

backup collection present
    → replace the corresponding portable collection

Do not describe this as a union/append operation.

onboardingComplete

They represent destination-local consent/setup state.

Also never import:

active focus session

The HTML should explain this as a portability boundary, not as a file corruption rule.

Important distinctions:

Defined/exported in legacy settings but not consumed by the legacy notification service.

Dead/session-local legacy code. Do not implement a temporary-preset import model based on it.

launcherWallpaperUri / overlayWallpaper

These are external/device-local resource references, not portable file content.

The destination keeps its local value and reports the resource as unresolved when appropriate; the importer must not install a dangling foreign-device URI.

22. focusMirrorVpnEnabled — presence-sensitive boolean

This field is intentionally portable.

Correct import semantics are equivalent to:

if the backup contains the key:
    use the backup value
else:
    keep the destination value

This means:

backup = false, local = true
→ result = false

and:

backup key absent, local = true
→ result = true

The common Kotlin mistake that behaves like:

imported || current

is wrong because it cannot represent an imported false winning over a local true.

The HTML should make this a concrete example because it is an easy field to implement incorrectly.

23. dailyAllowanceEntries

23.1 Canonical shape

Each entry is an object containing:

{
  "packageName": "com.example.video",
  "mode": "time_budget",
  "budgetMinutes": 30
}

The supported modes are:

count
time_budget
interval

Optional numeric fields:

countPerDay
budgetMinutes
intervalMinutes
intervalHours

23.2 Validation limits

Maximum entries:

1,000

For numeric fields:

countPerDay     1..100000
budgetMinutes   1..100000
intervalMinutes 1..100000
intervalHours   1..8760

26. greyoutSchedule — two different kinds of entries

greyoutSchedule is a mixed export representation.

It can contain:

A. user-authored greyout windows
B. derived windows generated from recurringBlockSchedules

These must not be treated the same way during import.

A user-authored window has no scheduleId.

Conceptual shape:

{
  "pkgs": [
    "com.example.social"
  ],
  "startHour": 22,
  "startMin": 0,
  "endHour": 23,
  "endMin": 30,
  "days": [1, 2, 3, 4, 5]
}

A legacy/user-created single-package representation may use pkg instead of pkgs:

{
  "pkg": "com.example.social",
  "startHour": 22,
  "startMin": 0,
  "endHour": 23,
  "endMin": 30,
  "days": [1, 2, 3, 4, 5]
}

Both shapes exist in the legacy model.

For new generated files, using pkgs consistently is straightforward and clear.

26.2 Derived window

A derived window carries:

scheduleId
scheduleName

and is generated from the authoritative recurring schedule.

Conceptually:

{
  "pkgs": ["com.example.social"],
  "startHour": 22,
  "startMin": 0,
  "endHour": 23,
  "endMin": 30,
  "days": [1, 2, 3, 4, 5],
  "scheduleId": "evening",
  "scheduleName": "Evening block",
  "vpnEnabled": false
}

26.3 Import rule

On import:

greyoutSchedule entry with NO scheduleId
    → portable user window
    → preserve/import

 greyoutSchedule entry WITH scheduleId
    → derived copy
    → discard

Then:

recurringBlockSchedules
    → restore authoritative schedules
    → regenerate derived greyout windows

This prevents duplicated/stale derived windows.

Window times use the same clock ranges:

startHour/endHour = 0..23
startMin/endMin   = 0..59
days              = distinct 1..7

5,000

32. Package-reference behavior

Package-name settings represent Android package identifiers.

They are portable identifiers, not promises that the destination device currently has the same app installed.

Therefore:

package referenced in backup
    ≠
package currently installed

The V1 policy is generally to preserve valid package references even when the package is absent on the destination.

Do not substitute an app label, package family, or “similar app.”

The HTML builder should validate syntax, not require the package to be installed on the machine running the web page.

33. External resources: wallpaper URIs

The backup may historically carry fields such as:

launcherWallpaperUri
overlayWallpaper

These refer to external/device-local resources.

A .focusflow file does not contain the referenced image bytes.

Therefore importing a foreign-device URI would create a dangling reference.

V1 policy:

keep the destination device's local wallpaper value
record the imported resource as unresolved
report the unresolved-resource count

Do not silently turn the backup URI into the destination's local URI.

Do not claim the .focusflow format embeds wallpapers.

39. Task merge semantics

39.1 New task ID

If the incoming task ID does not exist locally:

preserve incoming ID
insert task

39.2 Same ID + identical content

If the task ID already exists and its semantic duplicate projection is equivalent:

duplicate
skip incoming record
existing task wins

39.3 Same ID + divergent content

In V1 Merge mode:

whole restore is rejected before mutation
PlanFailure.IdConflict
journal is not written
persistent state is unchanged

The UI should show which tasks conflict (up to the configured display limit) and guide the user toward Replace mode when appropriate.

This is deliberate product semantics; it is not merely copying the legacy INSERT OR IGNORE database behavior.

For merge conflict detection, semantic task comparison includes:

tags

createdAt and updatedAt are excluded from this projection.

This means reminder-only differences do not create an ID conflict in V1.

The HTML should explain this clearly if it offers a technical import-behavior section.

For semantic comparison:

The HTML does not need to expose the hashing implementation, but a developer-focused page may explain that repeated-import detection is semantic rather than byte-for-byte JSON equality.

41. Replace mode

The UI label is:

Replace tasks

It does not mean “replace the entire app.”

Replace semantics concern the persistent task-owned task list.

41.1 What Replace changes

existing task rows
    → deleted

incoming valid backup tasks
    → restored

41.2 What Replace does NOT touch

It does not intentionally delete:

analytics
history tables
focus session history
PIN state
local consent
other device-local runtime state

41.3 Active session guard

Replace is prohibited while a Focus Session is active.

This condition is checked against runtime/DB session state, not merely a UI timer.

42. Repeated import behavior

Deliberately importing the same V1 file again is allowed.

Expected task behavior:

new tasks on first import
identical task IDs → skipped on subsequent import

Portable settings are re-applied according to their field policies.

There is no permanent “this file was imported once, never import again” file-level dedupe rule.

This also means the HTML should not add an artificial backup fingerprint requirement to the format itself.

43. Import-time normalization of old scheduled tasks

At restore-plan creation, capture a single planning time:

planNow

Then:

scheduled/active + endTime > planNow
    → scheduled

scheduled/active + endTime <= planNow
    → skipped
    → updatedAt = planNow

Other statuses remain unchanged.

A generated file may contain old tasks with past timestamps; that does not automatically make the file invalid.

The import behavior, however, means the generated example should generally use future or current timestamps if it is intended to demonstrate a live scheduled task.

44. Alarm and notification information: what belongs in the HTML format page

The .focusflow file itself does not contain authoritative Android AlarmManager registrations.

Nevertheless, the HTML may contain a concise “what happens after import” section because it explains why task data in a file can recreate useful behavior without serializing OS objects.

44.1 Task-end alarms are derived

For future imported tasks in scheduled/active-compatible state, the destination app recreates task-end alarms from task persistent truth.

44.2 Exact timing policy

Final V1 product contract:

task-end alarm = exact-timing product commitment

If exact capability is unavailable:

persist task normally
→ do NOT silently downgrade task-end timing
→ mark DEFERRED_EXACT_UNAVAILABLE
→ surface capability guidance
→ retry when exact capability returns

The inexact setAndAllowWhileIdle() ladder is not the task-end V1 policy.

Advisory reminder notifications may use a degraded/inexact tier because their timing is approximate by nature.

44.3 Task.reminders[] does not drive the Android scheduler

Generic reminder notifications are derived from task times through the separate reminder planner/chain.

The format page should keep this separate from the persistent reminders field.

45. Reminder notification derivation after import

This is useful context for a complete format page but should be labeled as runtime behavior, not wire data.

Current slot identifiers are based on task identity and relative times:

<taskId>-pre-600000   10 minutes before start
<taskId>-pre-300000   5 minutes before start
<taskId>-pre-60000    1 minute before start
<taskId>-pre0         at start
<taskId>-mid900000    15 minutes after start
<taskId>-mid1800000   30 minutes after start
<taskId>-almost       endTime − 60 seconds
<taskId>-end          at endTime (task-end alarm, not generic reminder)

Scheduling rules include:

  • do not schedule slots that are effectively already due (under the runtime scheduler's minimum lead time);
  • mid-session check-ins only when still before endTime and enough time remains;
  • global reminder slot budget: 450;
  • task-end alarm is handled separately from the generic reminder chain.

These identifiers do not belong in the .focusflow envelope as OS registrations.

46. The single-alarm reminder chain

The current runtime contract uses a single chain alarm for generic reminder notifications:

ReminderPlanner
    → earliest future reminder slot
    → one AlarmManager chain alarm
    → ReminderReceiver
    → recompute from DB
    → post due slots
    → ledger dedupe
    → re-arm next slot

The chain is runtime infrastructure.

The .focusflow generator should never attempt to serialize the chain's PendingIntent, registry, or ledger state.

47. Device/system protected packages — how the HTML should handle this topic

The older .focusflow HTML page includes a SYSTEM_NEVER_BLOCK package list and describes several Android package IDs as permanently exempt.

For this authoritative V1 file-format specification, do not treat that hardcoded package list as part of the .focusflow wire format unless the corresponding current source list is independently verified.

The important portable-format fact is:

package references are serialized as package IDs

and valid package syntax is enforced as described in §10.

System-level exemptions are runtime enforcement behavior, not fields inside the JSON envelope.

If the public website wants a separate “FocusFlow protected system apps” article, that can exist independently of the .focusflow format specification and must use independently verified current source.

52.1 “Exactly these top-level keys” is wrong

The current docs say every .focusflow file must contain exactly the listed top-level keys.

Correct statement:

kind, settings, and tasks are the structural core.
version is canonical but optional on input.
recognized metadata fields are optional.
unknown top-level fields are tolerated in compatible V1 input.

52.2 summary.taskCount is not authoritative

The current docs imply that a mismatch can make import fail.

Correct:

summary is informational.
tasks.length is authoritative.

The builder should calculate summary values but should not use them as schema gates.

52.3 Task durationMinutes is overclaimed

The current HTML says the duration must match the timestamp difference as an importer requirement.

The current parser verifies only:

0 <= durationMinutes <= 100000
endTime >= startTime

The builder should still generate coherent values, but the docs must not claim a stricter parser rule than the source implements.

52.4 focusAllowedPackages: [] is misexplained in old material

For Task records:

null/omitted → global allow-list
[]           → all apps allowed for that task
[packages]   → those specific packages

Do not teach [] as “block everything.”

52.5 Current example includes non-portable live-state keys

Old examples include fields like:

focusModeEnabled
pomodoroEnabled
notificationsEnabled
onboardingComplete
standaloneBlockPackages

These do not belong in canonical portable V1 settings.

They should appear only in an explicit “legacy/device-local fields that are ignored” section.

52.6 defaultReminderOffsets is not active scheduler configuration

Do not present it as the way to configure current task reminder delivery.

It is accepted/ignored compatibility data.

52.7 dailyAllowanceMs should not be the primary public wire example

The current builder uses:

"dailyAllowanceMs": 0

The canonical public shape should instead use:

packageName
mode
countPerDay
budgetMinutes
intervalMinutes
intervalHours

dailyAllowanceMs is an internal/legacy compatibility representation.

52.8 “Import replaces all existing data” is wrong

The app has:

MERGE
REPLACE TASKS

Portable settings use their own field policies.

Replace does not mean wiping analytics/history/PIN/runtime state.

52.9 “The file contains the whole state” is wrong

The format intentionally excludes runtime/device-local information.

The documentation should say:

portable persistent state

not:

entire device/app state

52.10 Color “codes reference” must be labeled correctly

The current parser does not impose a formal hex-color enumeration.

Recommended colors may be shown as design examples, but the page must not imply that only those six colors are legal.

52.11 System-protected package list should not be part of the core format contract

A hardcoded runtime exemption list is not a JSON field.

Keep it separate from the wire-format page unless its current source is independently verified.

61. Destination-device behavior that cannot be simulated purely from the HTML

The HTML builder can validate the file itself, but cannot know without app/device state:

whether an incoming task ID already exists locally
whether a same-ID task is identical or divergent
whether Replace is currently blocked by an active Focus Session
whether the imported settings weaken the destination's protected configuration
whether the destination has exact alarm capability
whether notifications are currently permitted
whether FSI is available
whether imported package IDs are installed

The UI should therefore phrase these as:

“FocusFlow will check this on import.”

not as browser-side facts.

62. Security guidance for the public documentation

The .focusflow format is a user-controlled input format.

The HTML should recommend:

  • keep backup files private if they contain personal task titles, profile data, package lists, or blocked words;
  • do not edit security/runtime fields expecting them to disable destination protections;
  • understand that old files may contain legacy device-local fields that FocusFlow intentionally ignores;
  • preserve a copy of an original backup before hand-editing it.

Do not describe .focusflow as encrypted or cryptographically authenticated unless that is separately implemented. V1 is plain JSON.

The core interoperability target is:

    ↓

    ↓

    ↓
Kotlin V1 restore

and, where supported:

Kotlin V1 export
    ↓

Cross-platform interoperability is about semantic parity, not byte-for-byte identical JSON formatting.

A canonical generator should therefore optimize for:

same persistent task state
same portable setting values

rather than relying on field order or whitespace.

64. HTML implementation details for the validator

The current builder uses a hand-written JavaScript duplicate-key scanner and structural checks. A future rewrite may use the same approach, but the content contract requires the behavior rather than a specific implementation.

64.1 Required duplicate-key detection

A normal JSON.parse() is insufficient because duplicate keys may be silently last-write-wins.

The browser-side validator must detect duplicates before accepting the document as clean.

64.2 Limits

Do not allocate an arbitrarily huge JSON tree before applying the file-size/complexity bounds.

A production-strength validator can apply:

byte count
maximum nesting
node count
task count
collection counts
string limits

before or during parsing.

64.3 JSON escaping

The builder must preserve valid JSON string escaping when formatting or downloading.

Do not “pretty format” by string manipulation that can break escaped quotes, newlines, backslashes, or Unicode.

72. Final implementation/content principle

The finished public HTML should communicate this model:

.focusflow
   = versioned UTF-8 JSON
   = portable FocusFlow persistent state
   + informational metadata
   - runtime state
   - device-local secrets/state
   - Android scheduler registrations
   - external resource contents

The core object model is:

Envelope
 ├── settings
 │    ├── portable scalar settings
 │    ├── package lists
 │    ├── allowance entries
 │    ├── presets
 │    ├── recurring schedules
 │    ├── greyout windows
 │    ├── userProfile
 │    └── launcher/protection preferences
 │
 ├── tasks[]
 │    ├── identity + content
 │    ├── absolute UTC timestamps
 │    ├── persistent status/priority
 │    ├── tags
 │    ├── inert reminders[]
 │    └── optional focus configuration
 │
 ├── presetSections    → inventory only
 └── summary            → informational only

The single most important design rule is:

Persistent portable truth
        ≠
Runtime/device state
        ≠
Derived Android state

That distinction is what keeps a .focusflow file portable, safe to edit, and predictable to import.
