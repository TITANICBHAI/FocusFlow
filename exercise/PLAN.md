## 0. Ground rules (read first, apply everywhere)

1. **A task without subtasks must behave and look exactly as it does today.** Same UI, same
   exports (byte-for-byte for tasks with no subtasks), same alarms, same analytics. All new UI
   appears only when `task.subtasks` is non-empty.
2. **Do not touch enforcement code** (`enforcement/`, accessibility service, VPN, alarms,
   launcher). The only allowed contact points are listed in §9.
3. **Never store image bytes in the `tasks` table or inside `Task`.** Images are files in
   app-private storage; the task row only holds small references. (Reason: `observeAllTasks()`
   does `SELECT *` on every emission; SQLite cursor windows are ~2 MB per row and the whole
   Home list would break.)
4. **Ticking a subtask is not a task mutation.** It must not call `reconcileAlarms`, must not
   bump `updatedAt`, must not run the scheduler/auto-reschedule, and must not clobber other
   task columns (see §5.3).
5. **Import must stay fail-soft.** A bad subtask or bad image never rejects the task, and a bad
   task never rejects the file (existing behavior in `BackupSerializer.parseAndValidate`).
   Surface problems as warnings on the import review screen.
6. **No new heavy dependencies.** Do not add Coil/Glide/Markdown libs. Image decode is a small
   in-house loader (§7.4).
7. **Theme-correct UI.** Use `MaterialTheme.colorScheme` and the `Ref*` tokens
   (`ui/home/ReferenceUi.kt`), `scaledSp` for all text sizes (per-screen text-scale feature),
   and `ui/theme/ResponsiveUi.kt` dimensions. Note `TaskCard.kt` hardcodes `Dark*` colors for
   its card background — do NOT copy that into new UI; new composables must look right in
   light and dark.
8. Every phase ends with: unit tests green (`./gradlew testProductionDebugUnitTest` and
   `testTbtechsdevDebugUnitTest`), `lint` clean (`abortOnError = true`, `NewApi` is an error),
   and a release-minified compile check (`assembleProductionRelease` must at least compile —
   new `@Serializable` classes must survive R8). Do not proceed to the next phase with red tests.
9. Anything you cannot verify without a device (rendering, Photo Picker, haptics, keep-screen-on)
   must be listed in your final report as "needs device check" — do not claim it passed.

## 1. Vision (owner's words, condensed)

The owner's schedule is mostly exercise. Instead of one task per exercise, they want a task to be
a **session** (e.g. "Upper body A") containing several **subtasks** (one per exercise) that can be
ticked individually. Opening a subtask shows an **image with an explanation**, in whichever
format fits: **step-by-step** (Step 1 + explanation, Step 2 + explanation, each possibly with its
own image) or **all-in-one** (one image, explanation below, plus a **goal** — for exercise,
usually sets × reps). Subtasks **may or may not have steps**. The content is generated by an AI
agent and delivered through a `.focusflow` import file, so the **AI prompt and in-app help must be
updated**. UI quality must be top-notch. The existing task system stays as it is.

The feature must be generic (study chapters, recipes, chores) — "exercise" is the primary example
and the drives default wording, not a hard-coded domain.

### Non-goals (this plan)
- No recurrence rules, no exercise library/database, no video, no animated GIF, no cloud sync.
- No change to how tasks are scheduled, completed, skipped, extended, reminded, or blocked.
- No stats/analytics on subtasks (candidate follow-up, §13).
- No remote image fetching in v1 (see DECISION D3).

## 3. Product decisions

Implement the **Default** unless the owner says otherwise. Anything not in this table is decided in the body.

| # | Question | Default |
|---|---|---|
| D1 | Does ticking all subtasks complete the task? | **No.** Show a non-blocking "All done — Complete task" banner that calls the existing complete flow. Completing a task with unticked subtasks is allowed with no prompt. |
| D2 | Where do subtasks live? | Single JSON column `subtasks` on `tasks` (rejected alternative: separate tables, §4.2). |
| D3 | Image sources in v1 | (a) Embedded in the `.focusflow` file (`assets`), (b) attached in-app from the gallery. **No remote URLs in v1** — a `url` image is skipped with a warning. (Remote images need a fetch/cache layer + Privacy Policy change; offline use in a gym is the main case.) |
| D4 | Export includes subtasks + images? | **Yes**, so a backup round-trips. If the file would exceed the importer's own 8 MiB cap, re-encode images smaller, then drop images with a visible warning (§6.6). |
| D5 | Importing a file whose tasks already exist (same ID) | Existing behavior stays (skip duplicates). **New**: an opt-in checkbox on the review screen, default ON when applicable: "Add subtasks to N existing tasks that have none". It only fills tasks whose local `subtasks` is empty; it never overwrites. (Realistic flow: owner already imported the schedule, then gets a richer file.) |
| D6 | Keep screen awake on the subtask screen | **Yes**, only while that screen is visible (gym use). |
| D7 | Rest timer after a set | **Yes**, local in-screen countdown only (no service, no notification), with a toggle. Off if `restSeconds` is absent. |
| D8 | Explanation text format | **Plain text.** Blank line = paragraph; lines starting with `- ` render as bullets. No Markdown, no HTML. |

## 4. Data model

### 4.1 Domain classes (new file `data/model/Subtask.kt`)

```kotlin
@Serializable
data class Subtask(
    val id: String,                       // unique within the task, 1..64 chars, [A-Za-z0-9_-]
    val title: String,                    // 1..200
    val done: Boolean = false,
    val subtitle: String? = null,         // ≤120, e.g. "Chest · triceps"
    val goal: SubtaskGoal? = null,
    val setsDone: Int = 0,                // progress for goal.kind == "sets"; 0..goal.sets
    val image: SubtaskImage? = null,      // overview ("all together") image
    val layout: String? = null,           // "steps" | "overview" | null (auto)
    val explanation: String? = null,      // ≤4000, plain text (D8)
    val steps: List<SubtaskStep> = emptyList(),   // 0..30
    val tips: List<String> = emptyList(),         // "Form cues", ≤10 × ≤300
    val avoid: List<String> = emptyList(),        // "Common mistakes", ≤10 × ≤300
)

@Serializable
data class SubtaskGoal(
    val kind: String,                     // "sets" | "reps" | "duration" | "distance" | "text"
    val sets: Int? = null,                // 1..99
    val reps: Int? = null,                // 1..9999
    val seconds: Int? = null,             // 1..86400   (duration, or timed sets e.g. 3 × 30 s)
    val restSeconds: Int? = null,         // 0..3600
    val meters: Int? = null,              // 1..1_000_000
    val weightKg: Double? = null,         // 0..1000
    val label: String? = null,            // ≤80; required for "text"; extra note otherwise ("per side")
)

@Serializable
data class SubtaskStep(
    val title: String? = null,            // ≤120, e.g. "Starting position"
    val text: String,                     // 1..1500
    val image: SubtaskImage? = null,
)

@Serializable
data class SubtaskImage(
    val asset: String,                    // asset id (see §4.3)
    val alt: String? = null,              // ≤200, used as contentDescription
)
```

Goal rules by `kind`: `sets` ⇒ `sets` required and (`reps` or `seconds`) required; `reps` ⇒ `reps`;
`duration` ⇒ `seconds`; `distance` ⇒ `meters`; `text` ⇒ `label`. An invalid goal is dropped with a
warning; the subtask itself survives. `GoalFormatter` (new, pure, unit-tested) turns a goal into
display strings: `3 × 12`, `3 × 30 s`, `45 s`, `2.5 km`, `12 reps`, plus `Rest 60 s`.

Rendering mode (pure function `SubtaskLayoutPolicy.resolve(subtask)`):
- `layout == "steps"` and `steps` non-empty ⇒ **Steps mode**
- `layout == "overview"` ⇒ **Overview mode**
- `null` ⇒ Steps mode if `steps` non-empty, else Overview mode
- Overview mode with `steps` present still lists the steps as a numbered text list under the image.

### 4.2 Storage: JSON column on `tasks`

- `Task` gets one new last parameter: `val subtasks: List<Subtask> = emptyList()` annotated
  `@EncodeDefault(EncodeDefault.Mode.NEVER)` (opt in to `ExperimentalSerializationApi`) so exports of
  tasks without subtasks stay byte-identical to today (the backup Json uses `encodeDefaults = true`).
- `TaskEntity` gets `@ColumnInfo(name = "subtasks", defaultValue = "[]") val subtasks: String`.
- Migration **9 → 10** (`MIGRATION_9_10` in `FocusFlowDatabase`, registered in `AppModule`):
  `ALTER TABLE tasks ADD COLUMN subtasks TEXT NOT NULL DEFAULT '[]'`. Guard with `PRAGMA table_info`
  like `MIGRATION_1_2` does. Bump `version = 10`, update the version-history table in the class KDoc,
  and **commit the generated `schemas/…/10.json`**.
- `TaskRepository`: map the column in both directions. Decode **per element** (parse a `JsonArray`,
  decode each element in its own `runCatching`, log and skip bad ones). Do NOT reuse `safeDecodeList`
  for subtasks: it would turn one unreadable element into `[]` and the next `updateTask` would
  permanently erase all subtasks.
- Decode cost: tasks are re-mapped on every Room emission. Add a small bounded memo
  (`SubtaskJsonCache`, ≤512 entries, key = raw JSON string) so unchanged rows are not re-parsed. Log
  decode time on a 300-task × 8-subtask fixture in a unit test (log only; no timing assertion).
- Size guard: serialized subtasks per task ≤ 96 KB UTF-8 (enforced at import and in-app writes).

Rejected alternative — separate `task_subtasks` / `task_steps` tables: better for lazy loading, but
costs a join + FK cascade + denormalized counters for the Home progress chip + restore-engine and
export plumbing, and `Task` would no longer be self-contained for the existing
`BackupEnvelope.tasks: List<Task>` path. Revisit only if measured memo-miss decode time becomes a
problem.

### 4.3 Images and assets

- **Files**: `context.filesDir/task_images/<sha256-hex>.webp` (content-addressed ⇒ automatic
  de-duplication; the same exercise image reused across 60 workout days is stored once).
- `Subtask.image.asset` / `SubtaskStep.image.asset` hold the **sha256-hex** at rest (DB). In the
  `.focusflow` file they hold **file-local asset ids** that point into the top-level `assets` map
  (§6). The import remaps file ids ⇒ sha256 ids before inserting tasks.
- New class `SubtaskImageStore` (in `data/images/`), injected via `AppModule`, with an `ImageCodec`
  interface (real impl uses `BitmapFactory`/`Bitmap.compress`; JVM tests use a fake):
  - `ingest(bytes): Result<String>` → validate, decode bounds, downscale, **re-encode**, write
    atomically (temp file + rename), return sha256 id.
  - `file(assetId): File?`, `exists(assetId)`, `openForExport(assetId): ByteArray?`.
  - `sweep(referencedIds: Set<String>)` → delete files not referenced (§4.4).
- Ingest rules (security — treat the file as hostile):
  - Detect format by **magic bytes** (PNG, JPEG, WebP only); ignore declared `mime`; reject SVG/GIF/other.
  - `inJustDecodeBounds` first; reject if either side > 4096 px or pixels > 16 MP; then decode with
    `inSampleSize` so the long edge ≤ **1280 px**.
  - Always re-encode (strips EXIF/GPS). Format: `Bitmap.CompressFormat.WEBP_LOSSY` on API ≥ 30,
    legacy `WEBP` on API 29 (minSdk 29). Quality 80.
  - Never use asset ids from the file as file names or paths.
  - Max 6 MiB total decoded asset bytes per import; max 200 assets; per-asset base64 ≤ 400 000 chars.

### 4.4 Orphan cleanup
`SubtaskImageStore.sweep` runs (a) after replace-import and delete-all-tasks, (b) after deleting a
task, (c) once per app start in the background. It collects every `asset` id referenced by all tasks'
subtasks and deletes unreferenced files **older than 10 minutes** (grace period so an in-flight import,
which writes files before inserting tasks, is never raced).

- `done=true` and `goal.kind=="sets"` ⇒ `setsDone = goal.sets` (consistency when toggled manually)
- strings trimmed; control chars except `\n` removed; blank optional strings ⇒ `null`
- list/size/char limits from §4.1; over-limit lists truncated **with a warning count**, never silent

### 6.2 Rules (what the importer enforces — mirror these in the prompt and help text)
- `subtasks` optional; `[]` or missing = none. Generated files set `done:false`, omit `setsDone`.
- Each subtask needs `title`; everything else optional. Unknown fields inside subtasks/goal/steps are
  ignored (no failure) but the **prompt tells the AI not to add any**.
- `assets`: map of id → `{mime, data}`. Ids match `^[A-Za-z0-9_-]{1,64}$`. `data` = raw base64.
  An `image.asset` pointing at a missing id ⇒ subtask imports without that image + warning.
  Unreferenced assets ⇒ ignored + one warning.
- `image.url` (or any non-`asset` image form) ⇒ image skipped + warning "remote images aren't supported".
- Nesting depth stays ≤ 8 (limit is 12). Whole file still ≤ 8 MiB.

### 6.3 Limits (add to `BackupJsonLimits`)
```

MAX_SUBTASK_TITLE_CHARS = 200  MAX_SUBTITLE_CHARS = 120        MAX_EXPLANATION_CHARS = 4_000
```

### 6.4 Preflight scanner change (important)
`BackupJsonPreflight.Scanner` currently applies `MAX_STRING_CHARS = 20_000` to every string, so any
embedded image would be rejected. Make the cap **context-aware**: thread a `StringContext` through
`parseValue/parseObject/parseArray/parseString`. A string value gets the larger
`MAX_ASSET_DATA_CHARS` cap **only** when it is the value of key `data` inside an object that is a
direct child of the top-level object's `assets` key (path: root → `assets` → `<id>` → `data`). Every
other string keeps 20 000. Keep duplicate-key and depth checks unchanged. Add scanner tests: long
string at `assets.x.data` accepted; same long string anywhere else (including `assets.x.mime`, task
fields, nested `assets` key inside a task) rejected.

### 6.5 Parsing (`BackupSerializer.parseAndValidate`)
- Add `assets: Map<String, BackupAsset> = emptyMap()` to `BackupEnvelope`
  (`@Serializable data class BackupAsset(val mime: String? = null, val data: String)`), annotated
  `@EncodeDefault(NEVER)`. Parse validates structure/size only (no image decoding here).
- Tasks are currently decoded with `json.decodeFromJsonElement<Task>(taskElement)`. A malformed
  `subtasks` value would make the **whole task** malformed. Change to: copy the task object **without**
  `subtasks`, decode `Task` from it, then run a new `SubtaskParser` on the `subtasks` element:
  per-subtask `runCatching`, normalization (§5.4), limits (§6.3), image-reference validation against
  `assets`, producing `(List<Subtask>, List<String> warnings)`. Aggregate warnings ("3 subtasks
  skipped", "2 images missing", "1 remote image skipped") into counts, not one line per item.
- Return the file-local asset ids in the `Subtask.image.asset` fields at this stage; remapping happens
  at restore (§6.7).

### 6.6 Export
- `BackupSerializer.buildEnvelope(settings, tasks, appVersion, assets)` gains `assets`. A new
  `SubtaskAssetExporter` collects referenced asset ids from tasks, reads bytes from
  `SubtaskImageStore`, and builds `assets` with deterministic ids (the sha256 hex is already a valid
  id; prefix with `i` if it would start with a digit — not required by the regex, so keep as is).
- Size control: compute total base64 size. If the projected file would exceed ~7 MiB, re-encode all
  images at max 960 px / q60; if still over, omit images (largest first) and return a user-visible
  warning "N images were left out to keep the file under 8 MiB". Never write a file the importer
  would reject.
- Tasks without subtasks export exactly as today.

### 6.7 Restore (`BackupRestoreEngine`)
1. Before taking the DB write gate: ingest all referenced assets via `SubtaskImageStore.ingest`
   (CPU/IO work, no DB). Build `fileId → sha256` map; failed assets ⇒ warning, image dropped.
2. Rewrite each imported task's subtasks with the sha256 ids.
3. Insert tasks as today (duplicate-ID skip unchanged).
4. **D5 enrich pass** (only if the review checkbox was ON): for each incoming task whose ID exists
   locally with empty `subtasks` and incoming non-empty `subtasks`, call `replaceSubtasks` (targeted
   column write, no alarm reconcile, other fields untouched, local `done` state irrelevant because
   local had none). Count them in the result summary. Never overwrite existing subtasks.
5. Sweep after replace-import. Surface counts: tasks imported, subtasks imported, images stored,
   tasks enriched, warnings.

### 6.8 Import review screen (`ImportConfirmScreen`, `BackupViewModel`)
- Summary line when the file has subtasks: "8 tasks · 52 subtasks · 31 images".
- Warning rows for skipped items (collapsed by default if > 3).
- D5 checkbox (shown only when ≥ 1 incoming task matches an existing ID with empty local subtasks and
  has subtasks): "Add subtasks to N existing tasks that have none" (default ON).
- Do not change the Merge/Replace semantics or copy.

## 7. UI/UX spec

Design intent: calm, high-contrast, glanceable mid-workout (phone propped up, sweaty thumbs, arm's
length). Large touch targets, big numerals, one primary action per screen, zero clutter. Accent color =

## 17. Phase 8 — Hardening of Phases 2–3 (revisions, additive)

Plan sections: §4.1, §4.3, §6, §11 (as revised below). Each item below becomes one tracker checkbox.

### 17.1 Fail-soft parsing at every nesting level
Expected behavior (write these as tests against `parseAndValidate` / `SubtaskParser`):

| Input | Required outcome |
|---|---|
| `assets.x` is not an object, or `data`/`file` is not a string, or `mime` is not a string | that asset dropped, one aggregated warning; other assets and all tasks import |
| `image` is `{"url": …}`, `{}`, or not an object (subtask or step level) | that image skipped, warning "unsupported image"; subtask/step kept |
| `steps[j]` has no `text`, or `text` is not a string | only that step dropped |
| `steps[j].image` invalid | only that image dropped |
| `goal` is not an object or fails its kind rules | goal dropped, subtask kept |
| `subtasks` is not an array | ignored with a warning; the task imports |
| `tips` / `avoid` contain non-strings | those entries dropped |

Implementation constraint: `assets` and each subtask element are interpreted from `JsonElement` (or typed
decoding wrapped per entry in `runCatching`). `BackupEnvelope.assets` must never be a typed
`Map<String, BackupAsset>` whose decoding can fail the whole envelope because of one bad entry. The
current code may already satisfy most rows; add the missing tests and fix only what fails.

### 17.2 Unknown-field warnings
Unknown keys stay non-fatal, but they must be **visible**. For every subtask, goal, step, image and asset
object, count keys outside the known set and add one aggregated warning, e.g.

### 17.3 Size budgets that actually add up (fixes an arithmetic error in §6.3)
Base64 inflates by 4/3, so the original "6 MiB decoded" budget alone equals the whole 8 MiB file cap.

```
MAX_ASSET_DATA_CHARS   = 400_000        (unchanged; ≈ 300 KB decoded per asset)
MAX_ASSET_TOTAL_BYTES  = 4 MiB          (was 6 MiB)  → ≈ 5.34 MiB as base64
JSON_NON_ASSET_RESERVE = 1 MiB          (new; room for tasks/text/overhead)
```

`ceil(MAX_ASSET_TOTAL_BYTES * 4 / 3) + JSON_NON_ASSET_RESERVE <= MAX_FILE_BYTES`, so the numbers can
never drift apart again. **Producer guidance for AI prompts** is stricter than the importer on purpose:
each image ≤ 100 KB, all images ≤ 3 MiB (was 150 KB / 5 MB).

### 17.4 Image fidelity and orientation
In the real `ImageCodec` (JVM tests use the fake codec; real behavior is an instrumented test):
1. **Apply EXIF orientation before re-encoding.** Read it with `android.media.ExifInterface(InputStream)`
   (API 24+; minSdk is 29, no new dependency). Order: read orientation → read bounds → run the size/pixel
   checks using the **rotated** dimensions → decode with `inSampleSize` → rotate/flip with a `Matrix` →
   re-encode. Recycle intermediate bitmaps immediately. Without this, portrait JPEG photos display sideways
   because re-encoding strips the EXIF tag.
2. **Fidelity for diagrams.** PNG sources → `WEBP_LOSSLESS` on API ≥ 30; on API 29 use lossy at quality 90.
   JPEG/WebP sources → lossy quality 85 (was 80). Keep quality constants in one place.
3. Content address stays the sha256 of the stored (re-encoded) bytes. Exports must never re-encode again
   (see D11).
Tests: fake-codec test that orientations 6 and 8 swap width/height before the pixel-limit check; instrumented
test sources with a rotated-JPEG fixture and a text-bearing PNG (compile-only here; mark "needs device check").

### 17.5 Restore ordering and bounded memory
1. Compute which incoming tasks will actually be **inserted** (non-duplicate IDs) or **enriched** (D5), and
   ingest only the assets those tasks reference. A merge import whose tasks are all duplicates stores zero files.
2. Ingest assets **one at a time**: obtain the bytes of one asset, ingest it, release the reference, move on.
   Never hold more than one decoded asset or one decoded bitmap at once.
3. Run `SubtaskImageStore.sweep` after **every** import outcome (merge, replace, enrich, failed/aborted),
   not only after replace; the 10-minute grace period still protects in-flight work.
Tests: all-duplicate file with images ⇒ zero files written; a fake store asserts max concurrency of 1 and
that references are released; sweep invoked after merge.

## 18. Phase 9 — Hybrid bundle (`.focusflow` may be JSON **or** a ZIP)

### 18.1 Overview and container detection
- One extension (`.focusflow`), two containers, decided by content: bytes `50 4B 03 04` ⇒ ZIP bundle;
  otherwise the existing JSON path (BOM/whitespace handling unchanged). A ZIP that does not contain a valid
  `manifest.json` is rejected with a clear message.
- **Audit first** (grep for `MAX_FILE_BYTES`, `ACTION_VIEW`, `OpenDocument`): find every place that enforces
  the 8 MiB cap or a MIME/extension filter *before* reading the file — likely `BackupFileManager`,
  `BackupImportIntentRelay`, `ExternalBackupIntentPolicy`, the SAF picker, and the manifest intent filters.
  The cap must depend on the sniffed container: JSON ≤ 8 MiB (unchanged), bundle ≤ 64 MiB. Change a MIME
  filter or manifest entry only if the audit shows a bundle would otherwise be unreachable; record what was
  changed.
- Architecture (keep the review/restore flow unchanged): a small `BackupSource` stage turns either container
  into **(a)** the manifest JSON text and **(b)** an `AssetByteSource` that returns the bytes of one asset on
  demand:
  ```kotlin
  interface AssetByteSource : java.io.Closeable {
      fun open(assetId: String): ByteArray?     // bounded, may return null when missing/invalid
  }
  ```
  `InlineAssetSource` decodes base64 from the parsed JSON `assets`; `ZipAssetSource` reads one zip entry.
  Everything downstream (parse/validate, review screen, enrich, ingest, remap, sweep) is the existing code,
  now reading bytes through `AssetByteSource`.

### 18.2 Bundle layout
```
my-schedule.focusflow          (a standard ZIP archive)
├── manifest.json              required; a normal FocusFlowBackupV1 envelope with "version": 2
└── assets/
    ├── pushup-start.webp
    └── plank.png
```
`manifest.json` is the same envelope as the JSON format (§6) except asset entries point to files instead of
carrying base64:
```jsonc
"assets": {
  "pushup-start": { "file": "assets/pushup-start.webp", "mime": "image/webp", "sha256": "<64 hex, optional>" }
}
```
Rules:
- An asset has **exactly one** of `data` (inline base64, allowed for small images) or `file` (bundle only).
  In a plain JSON file, `file` is ignored with a warning. In a bundle, if both are present `file` wins and the
  extra `data` is ignored with a warning.
- `file` must match `^assets/[A-Za-z0-9._-]{1,100}$`, end in `.webp/.png/.jpg/.jpeg`, and exist in the archive;
  otherwise the asset is dropped with a warning. The declared `mime` is ignored; the format is decided by magic
  bytes (§4.3).
- Optional `sha256`: if present it must equal the SHA-256 of the entry bytes, else that asset is rejected with a
  warning. Exports always write it.
- Task/subtask/`assets` semantics, id rules, `image.asset` references, warnings, D5 enrich and remapping are
  **identical** to the JSON format.
- Entries other than `manifest.json` and `assets/…` (for example `__MACOSX/`, a README) are ignored and counted
  in one warning.

### 18.3 Safe ZIP reading (treat the archive as hostile)
Constants in `BackupJsonLimits`:
```
MAX_BUNDLE_BYTES               = 64 MiB     (the archive file)
MAX_BUNDLE_ASSETS              = 300
MAX_BUNDLE_ENTRIES             = MAX_BUNDLE_ASSETS + 1 (manifest) + 50 (ignored extras)
MAX_BUNDLE_ASSET_ENTRY_BYTES   = 2 MiB      (uncompressed, per image entry)
MAX_BUNDLE_MANIFEST_BYTES      = MAX_FILE_BYTES (8 MiB; same preflight scanner as JSON)
MAX_BUNDLE_UNCOMPRESSED_BYTES  = 80 MiB     (sum of everything read)
```
Procedure:
1. Copy the picked URI stream to `cacheDir/import_bundle/<random>.zip` through a **counting stream that aborts
   at `MAX_BUNDLE_BYTES`** (never trust `OpenableColumns.SIZE`). Open it with `java.util.zip.ZipFile` for random
   access. The temp copy lives as long as the review screen (it is needed again at confirm) and is deleted on
   confirm, cancel, ViewModel clear, and by a startup sweep of files older than 1 hour. Never keep it in
   `filesDir`.
2. Validate the central directory first: entry count ≤ `MAX_BUNDLE_ENTRIES`; reject the whole bundle if
   `manifest.json` is missing, duplicated, or encrypted; skip (and count) entries that are encrypted, use a
   compression method other than STORED/DEFLATED, are directories, have names containing `..`, a leading `/`,
   a backslash, a NUL, or a drive prefix, or are duplicate names.
3. **Never extract to disk by entry name.** Read an entry into memory through a bounded stream that stops at
   its cap (`MAX_BUNDLE_ASSET_ENTRY_BYTES` or `MAX_BUNDLE_MANIFEST_BYTES`) regardless of the sizes declared in
   the headers (headers can lie), and keep a running total against `MAX_BUNDLE_UNCOMPRESSED_BYTES`. An entry
   that exceeds its cap is dropped (asset) or fails the bundle (manifest) with a clear message.
4. Truncated/corrupt archives, a `PK…` file that is not a valid ZIP, an empty ZIP, and a zip-in-zip all fail with
   the normal "not a valid FocusFlow file" error, never a crash.
5. Assets are read lazily one at a time during ingest (§17.5), so peak memory is one entry plus one bitmap.

### 18.4 Bundle export (D10, D11)
- `BackupBundleWriter` writes `manifest.json` first (DEFLATED), then `assets/<assetId>.webp` entries (STORED —
  WebP is already compressed), using `ZipOutputStream` on the SAF output stream. The bytes written are the
  stored, already-normalized image files, unmodified. Use a fixed entry timestamp so output is deterministic.
  Each manifest asset carries `file`, `mime`, and `sha256`.
- Choice rule: any exported subtask/step with an image ⇒ bundle; none ⇒ the existing JSON exporter, unchanged
  (including version 1/2 rule from §17.6). The success message says which container was written and why
  (for example "Saved with images as a bundle").
- Size check before writing: manifest bytes + sum of stored image sizes + 64 KB overhead reserve must be
  ≤ `MAX_BUNDLE_BYTES`. If it is not, return a `TooLarge` outcome and show an explicit dialog: **Export without
  images** or **Cancel**. Do not re-encode, shrink, or omit images on your own.
- **Retire** the JSON "re-encode smaller, then drop images" size-control from the earlier export work. Remove the
  dead code and its tests, or keep it only if something else still calls it; record the decision. The JSON exporter
  never needs inline images again.
- `SubtaskAssetExporter` keeps its role of collecting referenced asset ids; bytes now come from
  `SubtaskImageStore.openForExport`.

### 18.6 Prompt, in-app guide, hosted guide, agent recipe

  with the notes: the output must be a real ZIP named `*.focusflow`; `manifest.json` at the archive root, images
